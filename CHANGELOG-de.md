- **1.11.0** Veröffentlichung auf PyPI: `pip install ai-powered-markdown-translator` und anschließend der Befehl `aipmt`, ohne das Repository zu klonen (2026-08-31):

  - **Das Ein-Datei-Skript wird zu einem installierbaren Paket.** `translate.py` wechselt vom Stammverzeichnis nach `src/aipmt/translate.py`, mit einem Console-Entry-Point `aipmt` und dem Äquivalent `python -m aipmt`. Das geklonte Repository bleibt für Beiträge erforderlich — Tests, 28 Übersetzungen und Qualitätssicherung befinden sich dort — aber nicht mehr für die Nutzung.

    - **Der Importname ist `aipmt` und niemals `translate`**, weil die Kollision real und still ist. Das PyPI-Paket `translate` (v3.8.1, letzter Upload 2026-07-06) installiert ein VERZEICHNIS mit demselben Namen. In einer venv reproduziert: Das Verzeichnis hat Vorrang vor dem Modul, `translate.main` verschwindet, der Entry-Point scheitert bei `AttributeError` — und `pip check` antwortet mit „No broken requirements found“ bei rc=0. Ein einfaches `pip install translate` beim Benutzer hätte genügt, um die CLI ohne brauchbare Diagnose unbrauchbar zu machen. Gegenprobe mit dem echten Wheel: `pip install translate` über dem Paket, `aipmt --help` rc=0 davor und danach, beide CLIs koexistieren.
    - **Langer Distributionsname, kurzer Befehl.** `ai-powered-markdown-translator` macht das Paket über eine PyPI-Suche auffindbar; ein alleinstehendes Akronym wäre für Personen, die das Projekt noch nicht kennen, nicht auffindbar, und genau das Auffinden ist das Ziel der Veröffentlichung. Zwei plausible Kandidaten wurden durch Überprüfung ausgeschlossen: `ai-markdown-translator` ist seit 2024 auf npm von einem Tool mit demselben Zweck BELEGT, das 17 Monate älter als dieses Repository ist; und `aimt` unterscheidet sich nur durch einen Buchstaben von `aim` (v3.29.1), einem aktiven Paket aus DEMSELBEN Bereich — die schlechtestmögliche Konfiguration für eine dauerhafte Verwechslung. Methodische Falle nebenbei: `pypi.org/project/<nom>/` liefert für jeden Namen 200 (Anti-Bot-Seite), nur die JSON-API ist maßgeblich.
    - **Layout `src/` statt flachem Paket.** Das flache Paket hätte die sechs `sys.path.insert(..., "..")` der Tests beibehalten, und genau das ist der Fehler: Sie lassen den Quellbaum statt des Pakets importieren, wodurch jeder Packaging-Fehler verborgen würde. Tatsächlicher Aufwand: eine zusätzliche Ersetzungsregel.

  - **Korrektur — der `.env` des Benutzers wurde nach der Installation des Tools einmal ignoriert.** `load_dotenv()` ohne Argument sucht nicht vom aktuellen Verzeichnis aus nach oben, sondern von der AUFRUFENDEN Datei, also von `site-packages`. Gemessen mit einem echten Console-Entry-Point, der aus einem Projekt mit eigenem `.env` gestartet wurde: `find_dotenv()` liefert `''`, und der Schlüssel wird nicht geladen, während `find_dotenv(usecwd=True)` ihn findet. Der Fehler existierte nicht, solange das Tool nur aus dem geklonten Repository ausgeführt wurde; die Veröffentlichung hätte ihn systematisch gemacht, mit einem einzigen Symptom: einem „fehlenden“ API-Schlüssel bei korrekter Konfiguration.

  - **Drei Gates wären grün geworden, obwohl sie aufgehört hätten, irgendetwas zu prüfen.** Sie wurden VOR der Verschiebung absichtlich verschärft: Ein Schutzmechanismus, der nach der Änderung geschrieben wird, die er abfangen soll, beweist nichts. Jeder ist auf dem ursprünglichen Repository grün und wird auf einer migrierten Kopie rot — beide Richtungen werden gemessen.

    - **Lizard ignoriert einen fehlenden Pfad kommentarlos**: rc=0, „0 file analyzed“. Das Komplexitäts-Gate wäre von 158 Funktionen / 2247 nloc auf 3 Funktionen / 34 nloc gesunken, mit einer Ausgabe von null Bytes. Der Scope ist nun ein Array, dessen jeder Eintrag auf Existenz geprüft wird.
    - **`coverage run --source=` bei einem fehlenden Modul schlägt nicht fehl**: Warnung nur auf stderr, rc=0 sowohl für unittest als auch für `coverage xml`, und der Bericht wird trotzdem veröffentlicht — von 1453 auf 141 Statements amputiert. Das Projekt hätte gesund gewirkt, weil es kaum noch analysiert wurde. Zwei Untergrenzen schützen den Bericht: die Gesamtsumme und die größte gemessene Datei.
    - **Die Sonde für die Aktualität der Übersetzungen ist gegenüber der Aufrufform strukturell blind**: Sie verankert sich an den argparse-Flags, genau an dem, was eine Dateiumbenennung nicht verändert. Reproduziert: Modul verschoben, die 15 README-Dateien dokumentieren weiterhin einen nicht vorhandenen Befehl, Urteil „keine veraltete Übersetzung“. Ein 7. Abschnitt prüft daher die FORM und nicht die Optionen, und der Lizard-Hook wird mit dem tatsächlichen Scope des Skripts abgeglichen — sein Schlüssel `files:` lässt pre-commit nicht fehlschlagen, wenn er nicht mehr matcht, sondern lässt ihn ÜBERSPRINGEN.

  - **`requires-python = ">=3.10"` ist keine bloße Behauptung mehr.** `sonar-project.properties` kündigte bereits 3.10-3.12 an, ohne dass dies jemals ausgeführt worden wäre, da auf dem Entwicklungsrechner nur 3.12 vorhanden war — ein interner Widerspruch, den die Veröffentlichung öffentlich gemacht hätte. Ein Test-Workflow führt die Suite nun unter 3.10, 3.11 und 3.12 aus, installiert dabei das PAKET und damit seine öffentlichen Grenzen.

Auch keine Obergrenze für `<N+1` — sie stünde in direktem Widerspruch zu `check-deps-fresh.sh`, das das Release-Gate bei jeder Verzögerung einer Major-Version scheitern lässt. Die Menge der Untergrenzen löst das Problem, und die Gegenprobe `openai==1.0.0` endet mit `ResolutionImpossible`, was beweist, dass die Kontrolle unterscheidet, statt alles zu akzeptieren. Außerdem verhindert eine Prüfung, dass die Version von `pyproject.toml` von der des CHANGELOG abweicht: PyPI erlaubt die Wiederverwendung einer Nummer nicht.

Die 318 Tests bestehen mit einer bytegenau identischen Liste von Bezeichnern vor und nach der Migration — das beweist, dass kein Test deaktiviert wurde, nicht das „OK“.

- **Regression behoben — `_NEWS_CITATION_REGEX` hatte exponentielles Backtracking.** Der Fix für mehrere Absätze hatte `(?:[ \t]*$|[ \t]+.*)` in die Wiederholung eingeführt: Die Aufteilung der Leerzeichen zwischen `[ \t]+` und `.*` ist mehrdeutig, und diese Mehrdeutigkeit vervielfacht sich von Iteration zu Iteration. Gemessen an `>   texte`-Zeilen — vollkommen legaler Markdown-Einrückung — die nicht zum Muster passen: **2.589 ms für 14 Zeilen** gegenüber 0,04 ms nach der Korrektur, mit einem Faktor von ~9 pro hinzugefügter Zeile. Im `--news`-Modus genügte ein langer, nicht konformer Blockquote, um die Übersetzung bis zum Job-Timeout einzufrieren, ohne erkennbare Ursache. Die Wiederholung verbraucht nun die gesamte Zeile in einem Stück (`\n^>(?![ \t]*—).*`), sodass es pro Iteration nur noch eine Matching-Möglichkeit gibt. Am realen Korpus von 231 Artikeln überprüft: **null Unterschiede** bei den Captures, dieselben 423 Zitate, die 14 mehrabsätzigen Textkörper weiterhin erweitert.

Ein Helper `probe()` erzwingt nun sowohl Exit-Code null **als auch** eine Endsentinel, und die Sonden verweigern eine Schlussfolgerung bei einer leeren Menge von Markern — eine Assertion über eine leere Menge ist immer wahr. Demonstration: Das Hinzufügen der oben genannten exklusiven Gruppe ließ die Provider-Flags durch ein `*_group` laufen, das die alte Regex `parser\.add_argument\(` nicht mehr matchte; **sechs von einundzwanzig Flags** fielen stillschweigend aus dem Prüfbereich, das Gate blieb grün.
