- **1.10.0** `--use_codex` provider (ChatGPT subscription quota), SDK and model updates, fix for multi-paragraph news citations (2026-08-29):

  - **Fixes resulting from this PR's review** — five review agents scrutinized the diff; all the issues below were **reproduced through measurement** before being fixed, and two of them were regressions introduced earlier in this same release.

    - **Regression fixed — `_NEWS_CITATION_REGEX` had exponential backtracking.** The multi-paragraph fix had introduced `(?:[ \t]*$|[ \t]+.*)` into the repetition: whitespace sharing between `[ \t]+` and `.*` is ambiguous, and this ambiguity multiplies from one iteration to the next. Measured on `>   texte` lines — perfectly valid Markdown indentation — that do not match the pattern: **2,589 ms for 14 lines** versus 0.04 ms after the fix, with a factor of ~9 for each added line. In `--news` mode, a long, nonconforming blockquote was enough to freeze translation until the job timed out, with no identifiable cause. The repetition now consumes the entire line as a single unit (`\n^>(?![ \t]*—).*`), leaving only one way to match each iteration. Verified against the real corpus of 231 articles: **zero difference** in captures, the same 423 citations, with all 14 multi-paragraph bodies still expanded.
    - **Two simultaneous provider flags silently incurred usage-based charges.** `--use_codex --use_mistral` was accepted; `_select_provider_client` checks Mistral first, while `_resolve_provider` prioritizes explicit booleans — both converged on Mistral. The user was therefore requesting their subscription quota but receiving usage-based billing, without any warning whatsoever: exactly the failure mode that `--use_codex` exists to prevent. All six provider flags now go through a `add_mutually_exclusive_group`. **Behavior change**: a command line combining two providers, previously accepted silently, now fails on `argument --use_mistral: not allowed with argument --use_codex`.
    - **The end-of-work gate passed when its probes crashed.** Four of the thirteen `scripts/check-release-ready.sh` checks followed the pattern “capture stdout, conclude if empty” without ever checking the exit code: an exception (renamed file, `FileNotFoundError`) wrote to stderr, left stdout empty, and the check concluded “nothing to report.” The “an `exit 0` proves nothing” trap reproduced inside the script written to prevent it. A `probe()` helper now requires both a zero exit code **and** an end sentinel, and the probes refuse to draw conclusions from an empty set of markers—an assertion over an empty set is always true. Demonstration: adding the exclusive group above routed the provider flags through an `*_group` object, which the old `parser\.add_argument\(` regex no longer matched; **six flags out of twenty-one** silently fell outside the scope, with the gate still green.
    - **The secret scan missed four of the six providers.** The `[A-Za-z0-9]` class excludes hyphens: `sk-proj-…` (the current OpenAI format) and `sk-ant-api03-…` broke at their second hyphen, and `AIza…` was not covered. Pattern expanded, `.secrets.baseline` excluded from the scan. Additionally, the `.env` guard queried `git diff --cached`, which only sees the index: an `.env` that was **already committed**—the worst case—would never appear there. It now queries `git ls-files`.
    - **The Codex “token warm-up” was not one.** Measured: `codex login status` does not touch `~/.codex/auth.json` (mtime and size unchanged), and its help text says “Show login status.” Yet the comment claimed it refreshed the token “once, sequentially,” thereby eliminating the risk of concurrent refreshes on a rotating single-use token. The stated protection did not exist; the comment now says what the code actually does, and the real mitigation remains `max_jobs=4`. The check now also honors `CODEX_BIN`, which it previously ignored—a machine without `codex` in its `PATH` failed as “not authenticated,” a misleading diagnosis.
    - **`.env` was sourced in a subshell.** `detect_provider` is called through command substitution, so its exports did not propagate back: a `GROK_BIN`, `GROK_HOME`, or `REGEN_MODEL` defined in `.env` remained invisible to reads performed in `main()`, which concluded “Grok binary not found” despite a correct configuration.
    - **Concurrency exceeded the stated limit by 50%.** The guard was placed after launching the README/CHANGELOG pair: a measured peak of **3 for `max_jobs=2`**. For Grok, whose weekly quota is shared with Chat/Imagine/Voice and cannot be measured, the script therefore failed to honor its self-imposed limit. The final count, meanwhile, was displayed without ever being compared with 28—a missing file went unnoticed.
    - **Grok output contract: a missing `stopReason` is now a failure.** The code applied “`end_turn` **or missing**” where the stated contract requires `end_turn`. A payload without the field—or whose field had been renamed by a CLI update—silently turned the guard into a no-op. Additionally, `max_turn_requests` is no longer classified as a rate limit (the turn budget has been exhausted: retrying reproduces the result at the cost of a 90-second wait), and `quota` has been removed from the rate-limit markers—for the reason already stated in the `_codex_is_rate_limited` docstring, though Grok did not apply it.
    - **The Gemini fallback chain is memoized by model.** It restarted from `minimal` for every segment, even though the default model rejects it: the nominal path paid for a 400 round trip per segment and printed the same warning again. A warning repeated hundreds of times stops being read—that is how it becomes a smokescreen.
    - **Miscellaneous**: the CI rejection message was hard-coded for Codex and directed a `--use_grok_cli` user to `OPENAI_API_KEY` instead of `XAI_API_KEY`; `provider.capitalize()` displayed “Grok_cli” and “Openai”; the subprocess foundation comment generalized the “shim” to both CLIs even though the Grok binary is a native ELF (the correct rationale is “agent that spawns its own subprocesses”); twelve SAST findings on `subprocess` are marked `# nosec` / `# nosemgrep` with justification, since the list form without `shell=True` makes injection impossible and document content never passes through argv.
    - **No secrets are passed to agentic subprocesses anymore.** Named deny lists protected only the **billing** invariant (Codex without `OPENAI_API_KEY`, Grok without `XAI_API_KEY`). Measured: **seven other secrets** were still passed into every subprocess—the Anthropic, Mistral, Google, and Gemini keys, the other CLI's key, and `OPENAI_BASE_URL`, which is not a secret but redirects traffic. Yet these two CLIs are **agents**, and Grok's runs without an applicable OS sandbox on many Linux machines. Filtering is now performed **by name pattern** (`API_KEY`, `_TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIALS`) rather than by named list, which also covers variables users add to their `.env` without this code knowing about them. None are needed by the CLIs: authentication lives in `~/.codex` and `~/.grok`, never in the environment—verified through a **successfully completed real translation** using each of the two providers with the hardened environment.
    - **Tests**: new `tests/test_review_hardening.py` file (21 tests) locking down provider-flag exclusivity, the `stopReason` contract, news regex linearity, the CI rejection message, Gemini memoization, and the absence of all secrets from the subprocess environment. The latter assertion is **generic**—it fails on a key that no list names—whereas the existing scrubbing test mirrored its constant and could detect nothing except a failure in its own loop. Full suite now at **311 tests**.
  - **Two new Grok providers**: `--use_grok` (xAI API, `XAI_API_KEY` key, usage-based billing) and `--use_grok_cli` (official Grok Build CLI, deducted from the Grok subscription—the same principle as `--use_codex`).
    - **API mode, ~40 lines**: since the xAI endpoint is OpenAI-compatible, the client and `_call_openai` are reused as-is; only `base_url` changes. Only one adaptation was necessary, and it benefits everyone: `finish_reason` now accepts `end_turn`, the form emitted by xAI where OpenAI emits `stop`. Models: `grok-4.6` (quality) and `grok-4.3` (economy). Note that Grok's economy model remains the most expensive in the repository—$1.25/$2.50 per million versus $0.15/$0.60 for `mistral-small-latest`: this provider is chosen for model diversity, not price.
    - **CLI mode**: modeled after Codex, with four differences imposed by real-world constraints—the prompt is passed through a file (`--prompt-file`, the CLI does not read stdin, and a segment in argv would be visible in `ps`), the output is a single JSON object on stdout (neither JSONL nor a `-o` file), the subscription only provides `grok-4.6` and `grok-4.5`, and the sandbox cannot be applied (see below). Subprocess launching is shared with Codex in `_codex_run_process`, without touching the rest of the already-tested Codex provider.
    - **`exit 0` proves nothing, as measured**: when unauthenticated, the CLI writes `{"type":"error","message":"Not signed in."}` to **stdout** with exit code **0**. A refusal or exceeding the turn limit behaves the same way. The output contract therefore requires four simultaneous conditions: exit code 0, no error payload, `stopReason == end_turn`, and non-empty text. The preflight follows the same logic: `grok models` exits with 0 even when logged out; only the presence of “not authenticated” in stdout makes it possible to determine the status.
    - **Confinement: a deliberate and documented asymmetry.** While Codex runs in `--sandbox read-only`, Grok's sandbox is unusable on many recent Linux systems for two independent system-level reasons that cannot be worked around without `sudo`: AppArmor has blocked unprivileged user namespaces since Ubuntu 24.04 (`bwrap: setting up uid map: Permission denied`, reproduced outside Grok), and the container runtime socket denylist fails when `/run/podman` is in `0700` (the resolver only catches `ErrorKind::NotFound`; EACCES becomes fatal). The central trap: a **built-in** profile that cannot be applied **silently starts without confinement**. The script therefore requests no profile by default and never silently falls back—it warns on stderr. Protection relies on the CLI's `--deny` rules, including the `*` catch-all, the only measured _fail-closed_ layer (a rule with an unknown prefix causes startup to be refused). `GROK_TRANSLATE_SANDBOX=read-only` makes it possible to require it, in which case startup fails if the machine cannot honor it.
    - **Safeguards**: `XAI_API_KEY`, `GROK_API_KEY`, and `GROK_SANDBOX` are removed from the subprocess environment (a key would switch to usage-based billing; an inherited `GROK_SANDBOX` would impose an unusable profile with a misleading message), MCP/hooks/skills/agents switches are disabled, `--disable-web-search`, `--no-subagents`, `--no-plan`, disposable workdir, refusal to run in CI, timeout that kills the process group, and backoff on rate limits. `--max-turns` is set to 6 rather than 1: the counter is incremented after the tool turn, and 1 would truncate the output.
    - **Quota**: the Grok pool is weekly and **shared with Chat, Imagine, and Voice**, and no command exposes it—unlike Codex, whose `account/rateLimits/read` makes it possible to quantify usage. `regen_translations.sh` therefore limits concurrency to 2 and warns explicitly.
    - **Tests**: new `tests/test_grok_provider.py` file (24 tests). Full suite now at **290 tests**.
  - **Bug fixed—multi-paragraph EN quotes were only partially protected (`--news` mode)**: `_NEWS_CITATION_REGEX` accepted as the quote body only a sequence of **consecutive** `>` lines. As soon as a quote spanned multiple paragraphs (separated by an empty `>` line), only the last one was captured and replaced with the placeholder; the preceding ones were sent to the LLM and came back translated—the exact opposite of what `--news` exists to guarantee. The repetition now accepts internal empty `>` lines and is non-greedy, so it stops at the empty `>` preceding the italic line rather than at the first one encountered.
    - **Measured scope** on a real corpus of 198 articles: 11 affected quotes out of 419. No regression—the new regex captures exactly the same number of quotes; only multi-paragraph bodies are extended (408 identical bodies, 11 extended), and the `> — …` attribution line still cannot be absorbed into the body (lookahead retained).
    - **End-to-end proof** on a 69 KB article translated into ja/ar: the first paragraph of a quote, previously rendered as `> GLM-5.3がオープンウェイト化。` in Japanese and similarly translated into Arabic, now remains `> GLM-5.3 is now open-weight.`. The count of English quote lines returns from 9 to 10, matching the source.
    - Note: this defect was not detected by downstream validators, which verify the presence of the quote without checking that it is complete.
  - **Measured savings on the default provider**: `_openai_extra_kwargs` sent `reasoning_effort="medium"` whenever the model began with `gpt-5`, including in `--eco`. Measurement on `gpt-5.4-mini` when translating a ten-word sentence: `medium` → 45 reasoning tokens and 65 output tokens; `none` → 0 and 14. Reasoning adds nothing to a translation, and it was being paid for on every segment of every file. The default becomes `none` in `--eco` and remains `medium` otherwise; an explicit value passed through the CLI still takes precedence. `--reasoning_effort` now accepts `none` and `xhigh` in addition to `low`/`medium`/`high` (not all are accepted by every model: `minimal`, for example, is rejected by `gpt-5.4-mini`—the existing retry without the parameter handles this case).
  - **SDK updates and Gemini migration**: `google-generativeai` (support ended on 2025-11-30, repository archived) is replaced by the unified **`google-genai`** SDK—`genai.Client(api_key=...)` followed by `client.models.generate_content(model=, contents=, config=)`, with the system prompt passed through `system_instruction` instead of being concatenated with the segment. `mistralai` moves to **2.9.4** (the import becomes `from mistralai.client import Mistral`; the old one raises an `ImportError`, verified in the wheel), `anthropic` to **0.125.0**, and `openai` to **2.54.0**—the latest versions before the switch to `httpx2`, to avoid having two HTTP stacks coexist in the venv. `httpx` 0.28.1 and `pydantic` 2.13.5 are unblocked accordingly.

    - `anthropic` ≥ 1.0 rejects on the client side a non-streamed call whose `max_tokens` suggests more than 10 minutes (`ValueError: Streaming is required...`). This safeguard did not exist in 0.34.2 and broke every Claude call with `max_tokens=32768`. Fixed with an explicit `timeout` (`CLAUDE_TIMEOUT`, 900 s by default), which avoids switching to streaming for a call where only the complete response is used.
    - `thinking_level="minimal"` is accepted by only part of the Gemini catalog: `gemini-3.1-flash-lite` supports it, while `gemini-3.7-flash` and `gemini-3.1-pro-preview` reject it with a 400. Hence `_gemini_generate_with_fallback`, a `minimal` → `low` → no thinking_config fallback chain, modeled after the existing OpenAI fallback—an optimization parameter must never cause a translation to fail.

Strictly identical structure (21 lists, 18 code blocks, 13 HTML links, 13 images, all URLs preserved), in **8 s versus 48 s**. Since no public benchmark compares these two models on translation or non-Latin scripts, the switch would otherwise have rested on a mere assumption.
  - **Claude response-block filtering**: `_call_claude` performed `block.text for block in response.content` without filtering by type. Models with adaptive reasoning (Sonnet 5 and later) interleave a `thinking` block, which exposes `.thinking` rather than `.text`—the translation would have failed with an opaque `AttributeError` on the first segment. `thinking`, `redacted_thinking`, `tool_use`, and `tool_result` blocks are now excluded (a denylist, to remain tolerant of an unknown type carrying text), and a response without any text block raises an explicit error. `thinking={"type": "disabled"}` is passed with every call.

Addition of Claude 5 (`claude-sonnet-5`, `claude-opus-5`, `claude-fable-5`), `claude-opus-4-8`, Gemini 3.5/3.6/3.7, `mistral-medium-latest`, and the `ministral-*` range. Note: these limits remain indicative, as `translate()` caps segmentation at `min(16000, limite)`.

Translation usage is deducted from the already-paid ChatGPT subscription quota. This is the only path documented by OpenAI for this use case: the availability matrix by plan lists “Codex SDK, `codex exec`, and scriptable workflows” as available on Plus/Pro/Business/Enterprise, while `~/.codex/auth.json` tokens do not authenticate Platform API calls (and are never read by this script—the CLI continues to manage authentication and its refresh).
  - **Codex binary installable via pip, no longer only via npm**: `_resolve_codex_binary()` looks for the binary in `CODEX_BIN`, then `PATH`, then the official Python package **`openai-codex-cli-bin`** published by OpenAI (this is the dependency of SDK `openai-codex`). A Python project therefore no longer needs a global npm installation to use `--use_codex`. The package is not added to `requirements.txt`: the binary weighs ~250 MB, which would be imposed on all users for an optional provider. Verified end to end: with `codex` absent from `PATH`, resolution finds the packaged binary and completes a full translation in 6 seconds.
  - **“Subscription mode” guarantee**: `OPENAI_API_KEY` and `CODEX_API_KEY` are removed from the subprocess environment. Without this safeguard, a key present in `.env` could switch Codex to usage-based billing without any visible indication—exactly what this provider is designed to prevent.
  - **CLI pitfalls locked down by tests**:
    - `codex exec` reads stdin **even** when the prompt is passed as an argument: without closing stdin, the command waits until timeout without ever calling the model (reproduced: exit 124 after 180 seconds, zero bytes). `communicate(input=...)` is therefore mandatory.
    - The `codex` installed by npm is a Node shim that `spawn` the actual Rust binary: the latter is a **grandchild** of the Python process and survives the `SIGKILL` of `subprocess.run(timeout=)`, where it would continue consuming quota. Hence `Popen(start_new_session=True)` + `os.killpg`.
    - The CLI can exit with 0 while having emitted an `turn.failed`: the JSONL output (`--json`) is inspected in addition to the return code, and the absence of file `-o` with a 0 code raises an explicit error instead of producing an empty segment.
  - **Rate-limit backoff**: the CLI implements no internal retry (`max_retries = 0`). Classification is based on the JSON payload structure (`status: 429` / `error.type`), not substrings—the word “quota” appears both in a recoverable 429 and in a permanent `insufficient_quota`.
  - **CI safeguard**: `--use_codex` is rejected if `CI` or `GITHUB_ACTIONS` is set. Subscription authentication is not intended for a shared runner, and OpenAI explicitly advises against this workflow on public repositories.
  - **Models**: `gpt-5.6-sol` (quality) and `gpt-5.6-luna` (`--eco`). The `gpt-5.6-*` family is shared by the CLI and the Platform API, but a ChatGPT account is not entitled to all of it: the allowlist is enforced server-side, with no local validation, and an unusual model triggers a warning. On a Plus plan, Luna offers 250–2,000 messages per 5-hour window versus 10–100 for Sol: `--eco` is the recommended mode for all batch processing.

EXIT` referenced `failed_log`, a `local` variable from `main()` that no longer exists when the trap runs. Under `set -u`, this raised `failed_log: unbound variable` and caused the script to exit with 1 even though all 28 translations were correct—which would have interrupted `release.sh --auto` (`set -e`) immediately after regeneration, at the most costly step. The variable is now global, and the trap checks whether it exists. Useful side effect: genuine translation failures, previously masked by this error, are visible again in the final summary.
  - **`REGEN_MODEL`**: new `regen_translations.sh` environment variable that forces a specific model over the provider default, for example `REGEN_PROVIDER=codex REGEN_MODEL=gpt-5.6-sol` to regenerate using the subscription quota's high-end model rather than the volume-oriented `--eco` model.

The token is refreshed once sequentially before enabling parallelism—because the Codex refresh is rotating and single-use, concurrent jobs would invalidate session `codex login`—and concurrency is reduced to 4.

Explicit booleans continue to take precedence over `args` to preserve tests that call `translate(..., use_mistral=True)` with a minimal `Namespace`.

Full suite at 290 tests.

On a 69 KB news article in `--news` mode, both `gpt-5.6-luna` and `gpt-5.6-sol` pass the downstream application validator for en/ja/ar. Usage measured via `account/rateLimits/read`: remained below the counter's rounding threshold (0% of the 5-hour window) in `--eco` mode.

- **1.9.2** Fix news attribution URL extraction with nested parentheses or an FR prefix (2026-05-11):

  - **Fixed bug**: attribution URL extraction in `_protect_news_quotes` used the regex `re.search(r"\((.+?)\)", attribution)` (lazy capture between parentheses). On an attribution such as `(relayé par [@user sur X](https://x.com/.../123))` (nested parentheses: enclosing `(` + the Markdown link's `]()`), the capture stopped at the first `)` encountered → truncated string that also included the FR prefix: `relayé par [@user sur X](https://x.com/.../123` (without the final `)`). As a result, `_validate_news_post` looked for this string in the translated output and consistently failed (for two reasons: truncated `)` + “relayé par” translated as `relayed by`/`weitergeleitet von`/...). The complete low → medium → high → gpt-5.5 cascade could not pass.
  - **Fix**: the regex becomes `re.search(r"\]\(([^)]+)\)", attribution)`—specifically targets the Markdown link's `](url)`, capturing **only the raw URL** (without the FR prefix or truncation), an invariant preserved by `#URL{N}#` placeholders during translation. Robust against both problematic patterns:
    - `(relayé par [@account sur X](url))`—nested parentheses
    - `via [@source](url)` or `selon [@author](url)`—FR prefix without enclosing parentheses
  - **Tests**: 2 new tests in `test_silent_failure.py` class `TestNewsCitationExtraction`:
    - `test_extract_attribution_url_with_nested_parens` (exact reproduction of the Genspark CEO E2B bug)
    - `test_extract_attribution_url_with_french_prefix` (variant with `via`)
  - **Coverage gap**: `check-editorial-coverage.py` validates editorial syntax but not translatability by the translator. One possible improvement (outside the scope of v1.9.2) would be a check that simulates attribution extraction in a dry run to detect risky patterns BEFORE publication.

- **1.9** Silent-failure fix + comprehensive quality tooling + multi-position translation note (2026-05-07):
  - **Multi-position translation note + "embed card" marker format**:
    - New CLI options (additive, defaults unchanged → **non-breaking**):
      - `--note_position {top,bottom,both}` (default: `bottom`): places the note at the top, bottom, or both locations in the translated file.
      - `--note_format {legacy,marker}` (default: `legacy`):
        - `legacy` strictly reproduces the v1.8 behavior (bold paragraph `**…**`) **byte-for-byte**.
        - `marker` emits an invisible Markdown link reference definition (`[ai-translation-note-<placement>]: <> "v=1 source=… target=… model=… date=…"`) followed by a structured **3-paragraph blockquote** for "GitHub repo embed card"-style rendering: project title in inline code (`**\`ai-powered-markdown-translator\`\*\*`), description translated by the LLM, and CTA link (`[Voir le projet sur GitHub ↗](URL)`) with a visible arrow. Usable at build time by a remark plugin (see the jls42.org blog → `remark-translation-banner` plugin).
    - **Invariants never sent to the LLM**: the repository title and GitHub URL are assembled in Python after the descriptive sentence is translated.
