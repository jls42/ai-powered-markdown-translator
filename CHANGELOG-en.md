- **1.11.0** PyPI publication: `pip install ai-powered-markdown-translator` followed by the `aipmt` command, without cloning the repository (2026-08-31):

  - **The single-file script becomes an installable package.** `translate.py` moves from the root to `src/aipmt/translate.py`, with a `aipmt` console entry point and the equivalent `python -m aipmt`. The cloned repository remains necessary for contributing — tests, 28 translations, and quality tooling live there — but no longer for use.

    - **The import name is `aipmt` and never `translate`**, because the collision is real and silent. The PyPI package `translate` (v3.8.1, latest upload 2026-07-06) installs a DIRECTORY with the same name. Reproduced in a venv: the directory takes precedence over the module, `translate.main` disappears, the entry point breaks on `AttributeError` — and `pip check` responds “No broken requirements found” with rc=0. A simple `pip install translate` on the user’s system would have been enough to break the CLI without any actionable diagnosis. Counter-check on the actual wheel: `pip install translate` over the package, `aipmt --help` rc=0 before and after, both CLIs coexist.
    - **Long distribution name, short command.** `ai-powered-markdown-translator` makes the package findable through a PyPI search; an acronym alone would be unfindable to anyone who does not already know the project, whereas the publication is specifically intended to be discovered. Two plausible candidates were ruled out by verification: `ai-markdown-translator` has been TAKEN on npm since 2024 by a tool serving the same purpose, 17 months older than this repository; and `aimt` differs by one letter from `aim` (v3.29.1), an active package in the SAME domain — the worst configuration for lasting confusion. A methodological trap along the way: `pypi.org/project/<nom>/` returns 200 for any name (anti-bot page); only the JSON API is authoritative.
    - **`src/` layout rather than a flat package.** The flat package would have preserved the tests’ six `sys.path.insert(..., "..")`, and that is precisely the defect: they import the source tree instead of the package, which would hide any packaging error. The actual cost is one additional substitution rule.

  - **Keys can finally be configured once and for all.** An installed CLI had no PERSISTENT configuration: only the environment variable and the current directory’s `.env` remained. `find_dotenv` does search up to the system root and therefore found a `~/.env` **when working under the user’s home directory**, but found nothing when working elsewhere — coverage depended on where the command was launched from, not on a design choice. A third layer is therefore added: `~/.config/aipmt/.env`, below the two existing ones.

    - **The precedence is not hard-coded**; it follows from `override=False`, the default value of `load_dotenv`: each layer fills only what the previous one left empty. Hence the order environment variable → project’s `.env` → user configuration, verified by BEHAVIOR tests rather than structural tests — reversing the order of the two calls makes them fail, as does removing the third layer.
    - **`.env` format rather than TOML**, deliberately: `python-dotenv` is already a dependency, the syntax is already documented in the 15 READMEs, and the same file serves both scopes. No new dependency or syntax. The location follows `XDG_CONFIG_HOME` when it is **absolute** — the specification requires a relative value to be ignored, otherwise the configuration location would again depend on the current directory — and `APPDATA` on Windows.
    - **Two options rejected, with their reasons.** The system keyring (`keyring`) is safer on a desktop but fails in headless environments — server, container, CI — which is precisely the use case for batch translation; a good opt-in candidate, a poor default. A `--api-key` flag would put the key in the shell history and make it visible in `ps`.
    - **Without a key, no more call stack.** The user received a Python stack trace pointing to `site-packages`, and a message mentioning “the environment or .env” without saying where to create the latter. It now lists all three locations with their exact paths, and the command exits with 2. The safety net is **intentionally narrow**: `except ValueError` only around the configuration phase. Wrapping the entire execution would turn a real bug occurring during translation into a reassuring message — the failure mode this repository tracks. A test reads the source of `main()` to forbid it.

  - **Fix — the user’s `.env` was ignored once the tool was installed.** `load_dotenv()` without an argument searches upward from the CALLING file, not from the current directory, and therefore from `site-packages`. Measured with a real console entry point launched from a project with its own `.env`: `find_dotenv()` returns `''` and the key is not loaded, whereas `find_dotenv(usecwd=True)` finds it. The bug did not exist as long as the tool ran only from the cloned repository; publication would have made it systematic, with the sole symptom being an “missing” API key despite correct configuration.

  - **Three gates would have turned green while ceasing to verify anything.** They were hardened BEFORE the move, deliberately: a safeguard written after the change it is supposed to catch proves nothing. Each is green on the original repository and turns red on a migrated copy — both directions are measured.

    - **Lizard silently ignores a missing path**: rc=0, “0 file analyzed”. The complexity gate would have gone from 158 functions / 2247 nloc to 3 functions / 34 nloc, with a zero-byte output. The scope is now an array whose every entry is checked for existence.
    - **`coverage run --source=` does not fail on a missing module**: warning on stderr only, rc=0 for both unittest and `coverage xml`, and a report published anyway — reduced from 1453 to 141 statements. The project would have appeared healthy because almost none of it was being analyzed. Two floors protect the report: the total and the largest measured file.
    - **The translation-freshness probe is structurally blind to the invocation form**: it anchors itself to argparse flags, precisely what a file rename does not change. Reproduced: module moved, the 15 READMEs still documenting a nonexistent command, verdict “no stale translations”. A seventh section therefore checks the FORM rather than the options, and the Lizard hook is confronted with the script’s actual scope — its `files:` key does not make pre-commit fail when it no longer matches; it makes it SKIP.

  - **`requires-python = ">=3.10"` stops being an assertion.** `sonar-project.properties` already announced 3.10–3.12 without ever exercising any of them, since the development machine had only 3.12 — an internal contradiction that publication would have made public. A test workflow now runs the suite on 3.10, 3.11, and 3.12, installing the PACKAGE and therefore its public bounds.

  - **Lower bounds, no upper bound.** `requirements.txt` remains the tested lock, `[project.dependencies]` becomes the public contract: publishing the lock’s exact versions would cause conflicts for any user with other packages. No `<N+1` upper bound either — it would directly contradict `check-deps-fresh.sh`, which makes the release gate fail on any major-version delay. The set of lower bounds resolves this, and the `openai==1.0.0` counter-check exits with `ResolutionImpossible`, proving that the control discriminates instead of accepting everything. A separate guard prevents the version of `pyproject.toml` from diverging from the CHANGELOG version: PyPI does not allow reusing a number.

  - **Verified end to end in a fresh venv**: a 69,768-byte wheel containing only `aipmt/*.py`, the dist-info, and the license; `aipmt --help` rc=0 with 22 flags; `python -m aipmt` displaying “usage: aipmt” rather than “usage: \_\_main\_\_.py”; functional `pipx` installation; and above all **a real fr→en translation from an arbitrary user directory**, with bold, list, inline code, link, and URL preserved, and the code block untranslated. All 318 tests pass with a byte-for-byte identical identifier list before and after migration — that is what proves no test was neutralized, not the “OK”.

- **1.10.0** `--use_codex` provider (ChatGPT subscription quota), SDK and model updates, fix for multi-paragraph news citations (2026-08-29):

  - **Security review — two safeguards the PR introduced without enforcing them everywhere**:

    - **The Codex preflight passed the entire `.env` to the binary.** `_codex_preflight` called `subprocess.run` **without `env=`**: the subprocess inherited the entire `os.environ`, and therefore all of the `.env` loaded by `load_dotenv`. Measured with an instrumented fake binary: **seven secrets** reached the preflight — the keys for the six providers plus one `GITHUB_TOKEN` — versus **zero** for its `_grok_preflight` counterpart, which correctly passed `env=_grok_env()`. The inconsistency was internal to the PR: `_strip_secret_env` exists precisely to enforce this invariant, a few lines away. A shared `_codex_env_base()` is extracted for both paths; measurement after the fix: 0 secrets on either side.
    - **The “`--deny` fail-closed” property did not cover the form being used.** The comment justified all Grok confinement by claiming that an unknown-prefix rule causes startup to be rejected. Measured on `grok 1.0.13`, this validation exists **only for the parenthesized form**: `--deny 'CeciNestPasUnOutil(*)'` rejects startup (“unknown tool prefix”), whereas `--deny 'CeciNestPasUnOutil'` is silently accepted. But `GROK_DENY_RULES` used only bare names — an xAI-side tool rename would therefore have removed the only measured confinement layer without the slightest signal, on a machine where the OS sandbox already does not apply. The eight named rules pass through `Prefix(*)`, each verified as a known CLI prefix; the catch-all `*` remains in its literal form, the only accepted one. A test prevents reverting to the unvalidated form.
    - **Otherwise cleanly verified**: no command injection (list form everywhere, never `shell=True`, document content through stdin or `--prompt-file`), no unsafe deserialization (`json.loads` only, with a type guard), path-traversal fix with no bypass found across seven payloads, and `--deny '*'` actually enforced by the CLI (`DENY_ENFORCED` observed on a read outside the workdir).
    - The freshness check added above also bypassed its own principle: a package whose PyPI request failed was silently skipped, leaving the gate green. It now counts the packages actually compared and fails if coverage is incomplete.

  - **Dependencies upgraded, with two nets to prevent the delay from recurring**:

    - **The delay was real and lasting**: `openai` 2.54 → **3.6.0**, `anthropic` 0.125 → **1.2.0**, `certifi` 2024.8.30 → **2026.7.22** — two years behind on the root certificate store that validates TLS for all provider calls. Cause identified: **there was no `.github/dependabot.yml`**. Without this file, GitHub activates only _security updates_, and Dependabot proposes a PR only for a dependency targeted by a CVE — explaining why it bumped `urllib3` and `idna` while leaving two SDKs drifting from a major version.
    - **The two major versions coexist without conflict**, contrary to what earlier reasoning suggested: `openai` 3.x and `anthropic` 1.x migrate to **`httpx2`** when `mistralai` and `google-genai` remain on `httpx<1`, but they are two distinct distributions. Verified through an actual installation, then through **all 7 provider paths tested end to end** — OpenAI, Claude, Mistral, Gemini, Grok API, Codex CLI, and Grok CLI — with inline code and links preserved in every output. “Avoid two HTTP stacks” was a preference, not a blocker: measurement settled it.
    - **`requirements.txt` did not describe the real environment**: `google-auth`, `cryptography`, and the `opentelemetry` stack were installed in the working venv without ever being declared — so a fresh install did not reproduce what was tested. Conversely, `tokenizers`, `huggingface-hub`, and `PyYAML` appeared there without being imported or required by anything, remnants of `mistralai` 1.x. The file is regenerated as the complete closure of a venv built from direct dependencies alone. `pip-audit` reports no known vulnerabilities in the new set.
    - **`.github/dependabot.yml`** (new) enables weekly version, pip, and github-actions updates. Minor and patch updates are grouped into one PR — a patch bump per PR ends up ignored, and noise is the enemy of updating; **major versions are separate**, each requiring validation through an actual call.
    - **`scripts/check-deps-fresh.sh`** (new, wired into the gate) makes the delay visible in the project verdict: Dependabot proposes, it does not guarantee, and its PRs can pile up. Major-version delay → failure; minor → warning, because a permanently red gate eventually gets ignored; PyPI unreachable → explicit local skip and **fail-closed in CI**, since an unchecked control is not a success. Verified in both directions: it catches the exact pre-fix state (`openai 2.54.0→3.6.0`, `certifi 2024.8.30→2026.7.22`) and merely warns on a minor version.

  - **Fixes arising from this PR’s review** — five review agents scrutinized the diff; all points below were **reproduced by measurement** before correction, and two of them were regressions introduced earlier in this same version.
- **Fixed regression — `_NEWS_CITATION_REGEX` had exponential backtracking.** The multi-paragraph fix had introduced `(?:[ \t]*$|[ \t]+.*)` into the repetition: the sharing of whitespace between `[ \t]+` and `.*` is ambiguous, and that ambiguity multiplies from one iteration to the next. Measured on `>   texte` lines — perfectly legal Markdown indentation — that do not match the pattern: **2,589 ms for 14 lines** versus 0.04 ms after correction, with a factor of ~9 per added line. In `--news` mode, a long, non-conforming blockquote was enough to freeze the translation until the job timed out, with no identifiable cause. The repetition now consumes the entire line in one go (`\n^>(?![ \t]*—).*`), leaving only one way to match per iteration. Verified on the real corpus of 231 articles: **zero capture differences**, the same 423 quotes, and the 14 multi-paragraph bodies still expanded.
    - **Two simultaneous provider flags were silently billed on a usage basis.** `--use_codex --use_mistral` was accepted; `_select_provider_client` tests Mistral first, while `_resolve_provider` gives priority to explicit booleans — both converged on Mistral. The user therefore requested their subscription quota and received usage-based billing, without the slightest warning: exactly the failure mode that `--use_codex` exists to prevent. All six provider flags now pass through a `add_mutually_exclusive_group`. **Behavior change**: a command line combining two providers, previously silently accepted, now fails on `argument --use_mistral: not allowed with argument --use_codex`.
    - **The end-of-job gate turned green when its probes crashed.** Four of the thirteen `scripts/check-release-ready.sh` checks followed the pattern “capture stdout, conclude if empty” without ever consulting the exit code: an exception (renamed file, `FileNotFoundError`) wrote to stderr, left stdout empty, and the check concluded “nothing to report.” The trap “an `exit 0` proves nothing” was reproduced inside the script written to prevent it. A `probe()` helper now requires both a zero exit code **and** an end sentinel, and the probes refuse to conclude on an empty set of markers — an assertion on an empty set is always true. Demonstration: adding the exclusive group above caused the provider flags to pass through a `*_group` object, which the old `parser\.add_argument\(` regex no longer matched; **six flags out of twenty-one** silently fell outside the scope, with the gate green.
    - **The secrets scan missed four out of six providers.** The `[A-Za-z0-9]` class excludes the hyphen: `sk-proj-…` (current OpenAI format) and `sk-ant-api03-…` broke on their second hyphen, and `AIza…` was not covered. Pattern broadened, `.secrets.baseline` excluded from the scan. The `.env` guard also queried `git diff --cached`, which only sees the index: an `.env` that had **already been committed** — the worst case — never appeared there. It now queries `git ls-files`.
    - **The Codex “token warm-up” was not one.** Measured: `codex login status` does not touch `~/.codex/auth.json` (mtime and size unchanged), and its help says “Show login status.” The comment nevertheless claimed to refresh the token “once, sequentially,” thereby neutralizing the risk of concurrent refreshes on a single-use rotating token. The advertised protection did not exist; the comment now says what the code does, and the real workaround remains `max_jobs=4`. The check also honors `CODEX_BIN`, which it had ignored — a machine without `codex` in the `PATH` failed with “not authenticated,” a misleading diagnosis.
    - **`.env` was sourced in a subshell.** `detect_provider` is called in command substitution, so its exports did not propagate: an `GROK_BIN`, `GROK_HOME`, or `REGEN_MODEL` defined in `.env` remained invisible to reads performed in `main()`, which concluded “Grok binary not found” on a correct configuration.
    - **Concurrency exceeded the announced bound by 50%.** The guard was placed after launching the README/CHANGELOG pair: measured peak of **3 for `max_jobs=2`**. On Grok, whose weekly quota is shared with Chat/Imagine/Voice and cannot be measured, the bound imposed by the script was therefore not maintained. The final count, meanwhile, was displayed without ever being compared with 28 — a missing file went unnoticed.
    - **Grok output contract: a missing `stopReason` is now a failure.** The code applied “`end_turn` **or absent**” where the announced contract requires `end_turn`. A payload without the field — or whose field was renamed by a CLI update — turned the guard into a silent no-op. In addition, `max_turn_requests` is no longer classified as a rate limit (the turn budget is exhausted: retrying reproduces the result, at the cost of 90 seconds of waiting), and `quota` is removed from the rate-limit markers — for the reason that the docstring of `_codex_is_rate_limited` already stated, without Grok applying it.
    - **The Gemini cascade is memoized by model.** It restarted from `minimal` for every segment, even though the default model rejects it: the nominal path paid for a 400 round trip per segment and reprinted the same warning. A warning repeated hundreds of times stops being read — that is how it becomes a mask.
    - **Miscellaneous**: the CI refusal message was hard-coded for Codex and directed a `--use_grok_cli` user to `OPENAI_API_KEY` instead of `XAI_API_KEY`; `provider.capitalize()` displayed “Grok_cli” and “Openai”; the subprocess base comment generalized the “shim” to both CLIs even though the Grok binary is a native ELF (the correct justification is “agent that spawns its own subprocesses”); twelve SAST findings on `subprocess` are marked `# nosec` / `# nosemgrep` with justification, the list form without `shell=True` making injection impossible and the document content never passing through argv.
    - **No secrets enter agentic subprocesses anymore.** The named deny-lists protected only the **billing** invariant (Codex without `OPENAI_API_KEY`, Grok without `XAI_API_KEY`). Measured: **seven other secrets** still entered every subprocess — the Anthropic, Mistral, Google, and Gemini keys, the other CLI’s key, and `OPENAI_BASE_URL`, which is not a secret but redirects traffic. These two CLIs are **agents**, and the Grok one runs without an applicable OS sandbox on many Linux machines. Filtering is now done **by name pattern** (`API_KEY`, `_TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIALS`) rather than by named list, also covering variables a user adds to their `.env` without this code knowing about them. None is necessary for the CLIs: authentication lives in `~/.codex` and `~/.grok`, never in the environment — verified by a **successful real translation** through each provider with the hardened environment.
    - **Tests**: new file `tests/test_review_hardening.py` (21 tests) locking down provider-flag exclusivity, the `stopReason` contract, news-regex linearity, the CI refusal message, Gemini memoization, and the absence of any secret in subprocess environments. This last assertion is **generic** — it fails on a key that no list names — whereas the existing redaction test mirrored its constant and could detect nothing beyond a failure in its own loop. Full suite now at **311 tests**.

  - **Two new Grok providers**: `--use_grok` (xAI API, `XAI_API_KEY` key, usage-based billing) and `--use_grok_cli` (official Grok Build CLI, deducted from the Grok subscription — same principle as `--use_codex`).
    - **API mode, ~40 lines**: since the xAI endpoint is OpenAI-compatible, the client and `_call_openai` are reused as-is; only `base_url` changes. One adaptation was necessary and benefits everyone: `finish_reason` now accepts `end_turn`, the form emitted by xAI where OpenAI emits `stop`. Models: `grok-4.6` (quality) and `grok-4.3` (economy). Note that Grok’s economy model remains the repository’s most expensive — $1.25/$2.50 per million versus $0.15/$0.60 for `mistral-small-latest`: this provider is chosen for model diversity, not price.
    - **CLI mode**: modeled on Codex, with four divergences imposed by reality — the prompt is passed by file (`--prompt-file`, the CLI does not read stdin and a segment in argv would be visible in `ps`), the output is a single JSON object on stdout (neither JSONL nor `-o` file), the subscription exposes only `grok-4.6` and `grok-4.5`, and the sandbox cannot be applied (see below). Subprocess launching is factored with Codex into `_codex_run_process`, without touching the rest of the already-tested Codex provider.
    - **`exit 0` proves nothing, measured**: when unauthenticated, the CLI writes `{"type":"error","message":"Not signed in."}` to **stdout** with an **0** exit code. A refusal or exhausted turn budget behaves the same way. The output contract therefore requires four simultaneous conditions: exit code 0, no error payload, `stopReason == end_turn`, and non-empty text. The preflight follows the same logic: `grok models` exits with 0 even when disconnected; only the presence of “not authenticated” in stdout allows a conclusion.
    - **Confinement: deliberate and documented asymmetry.** Whereas Codex runs in `--sandbox read-only`, the Grok sandbox is inapplicable on many recent Linux machines for two independent system-level causes that cannot be worked around without `sudo`: AppArmor blocks unprivileged user namespaces starting with Ubuntu 24.04 (`bwrap: setting up uid map: Permission denied`, reproduced outside Grok), and the container-runtime socket deny-list fails when `/run/podman` is in `0700` (the resolver catches only `ErrorKind::NotFound`; EACCES becomes fatal). Central trap: an **integrated** profile that cannot be applied **starts unconfined silently**. The script therefore requests no profile by default and never falls back silently — it warns on stderr. Protection relies on the CLI’s `--deny` rules, including the `*` catch-all, the only measured _fail-closed_ layer (a rule with an unknown prefix causes startup to be refused). `GROK_TRANSLATE_SANDBOX=read-only` makes it possible to require this, in which case startup fails if the machine cannot honor it.
    - **Safeguards**: `XAI_API_KEY`, `GROK_API_KEY`, and `GROK_SANDBOX` are removed from the subprocess environment (a key would switch to usage-based billing; an inherited `GROK_SANDBOX` would impose an inapplicable profile with a misleading message), MCP/hooks/skills/agents switches disabled, `--disable-web-search`, `--no-subagents`, `--no-plan`, disposable workdir, CI refusal, timeout that kills the process group, backoff on rate limits. `--max-turns` is set to 6 rather than 1: the counter is incremented after the tool turn, and 1 would truncate the output.
    - **Quota**: the Grok pool is weekly and **shared with Chat, Imagine, and Voice**, and no command exposes it — unlike Codex, whose `account/rateLimits/read` makes it possible to quantify consumption. `regen_translations.sh` therefore limits concurrency to 2 and warns explicitly.
    - **Tests**: new file `tests/test_grok_provider.py` (24 tests). Full suite now at **290 tests**.
  - **Fixed bug — multi-paragraph EN quotes were only partially protected ( `--news` mode)**: `_NEWS_CITATION_REGEX` accepted, as a quote body, only a sequence of `>` lines that were **consecutive**. As soon as a quote spanned multiple paragraphs (separated by a blank `>` line), only the last was captured and replaced with the placeholder; the preceding ones were sent to the LLM and returned translated — the exact opposite of what `--news` exists to guarantee. The repetition now accepts internal blank `>` lines and is non-greedy, stopping at the blank `>` that precedes the italic line rather than at the first one encountered.
    - **Measured scope** on a real corpus of 198 articles: 11 affected quotes out of 419. No regression — the new regex captures exactly the same number of quotes; only multi-paragraph bodies expand (408 identical bodies, 11 expanded), and the attribution line `> — …` still cannot be absorbed into the body (lookahead preserved).
    - **End-to-end proof** on a 69 KB article translated into ja/ar: the first paragraph of a quote, previously rendered as `> GLM-5.3がオープンウェイト化。` in Japanese and likewise translated into Arabic, now remains `> GLM-5.3 is now open-weight.`. The count of English quote lines rises from 9 to 10, matching the source.
    - Note: this defect was not detected by downstream validators, which check for the presence of the quote without checking that it is complete.
  - **Measured savings on the default provider**: `_openai_extra_kwargs` sent `reasoning_effort="medium"` whenever the model started with `gpt-5`, including in `--eco`. Measurement on `gpt-5.4-mini` for translating a ten-word sentence: `medium` → 45 reasoning tokens and 65 output tokens; `none` → 0 and 14. Reasoning adds nothing to translation, and it was paid for on every segment of every file. The default becomes `none` in `--eco` and remains `medium` otherwise; an explicit value passed via the CLI remains higher priority. `--reasoning_effort` now accepts `none` and `xhigh` in addition to `low`/`medium`/`high` (not all are accepted by all models: `minimal`, for example, is rejected by `gpt-5.4-mini` — the existing retry without the parameter covers this case).
  - **SDK updates and Gemini migration**: `google-generativeai` (support ended on 2025-11-30, repository archived) is replaced by the unified SDK **`google-genai`** — `genai.Client(api_key=...)` followed by `client.models.generate_content(model=, contents=, config=)`, with the system prompt passed as `system_instruction` instead of being concatenated to the segment. `mistralai` moves to **2.9.4** (the import becomes `from mistralai.client import Mistral`; the old one raises an `ImportError`, verified in the wheel), `anthropic` to **0.125.0**, and `openai` to **2.54.0** — the last versions before the switch to `httpx2`, to avoid having two HTTP stacks coexist in the venv. `httpx` 0.28.1 and `pydantic` 2.13.5 are consequently unlocked.
  - **Two regressions caught by real tests, not by the documentation**:
    - `anthropic` ≥ 1.0 refuses on the client side a non-streamed call whose `max_tokens` suggests more than 10 minutes (`ValueError: Streaming is required...`). This safeguard did not exist in 0.34.2 and broke every Claude call with `max_tokens=32768`. Fixed by an explicit `timeout` (`CLAUDE_TIMEOUT`, 900 s by default), avoiding a switch to streaming for a call whose complete response is the only part used.
    - `thinking_level="minimal"` is accepted by only part of the Gemini catalog: `gemini-3.1-flash-lite` supports it, while `gemini-3.7-flash` and `gemini-3.1-pro-preview` reject it with a 400. Hence `_gemini_generate_with_fallback`, a cascade `minimal` → `low` → no thinking_config, modeled on the existing OpenAI fallback — an optimization parameter must never make a translation fail.
  - **Default models renewed**, each validated by a real call: OpenAI `gpt-5.5` → **`gpt-5.6-terra`** (−60% on a batch of 28) and `gpt-5.4-mini` → **`gpt-5.6-luna`** (−73%); Claude `claude-sonnet-4-6` → **`claude-sonnet-5`** (cheaper and newer) and `claude-haiku-4-5-20251001` → **`claude-haiku-4-5`** (canonical ID without date); Gemini `gemini-3.1-pro-preview` → **`gemini-3.7-flash`** and `gemini-3.1-flash-lite-preview` → **`gemini-3.1-flash-lite`** (stable version, and cheaper than `3.5-flash-lite`).
Mistral unchanged, `mistral-large-latest` remaining the best value for money of the four. Note: there is no newer Gemini Pro-tier model than `gemini-3.1-pro-preview` — Gemini 3.5 Pro, announced in May 2026, was never released; the 3.5/3.6/3.7 line is exclusively Flash.
  - **A/B measured before switching to Gemini**: `README.md` translated into Japanese with `gemini-3.1-pro-preview` and then `gemini-3.7-flash`. Strictly identical structure (21 lists, 18 code blocks, 13 HTML links, 13 images, all URLs preserved), in **8 s versus 48 s**. Since no public benchmark compares these two models on translation or non-Latin scripts, the switch would otherwise have been based on a simple assumption.
  - **Filtering Claude response blocks**: `_call_claude` used to perform `block.text for block in response.content` without filtering the type. Adaptive-reasoning models (Sonnet 5 and later) insert a `thinking` block, which exposes `.thinking` rather than `.text` — translation would have broken on an opaque `AttributeError` at the first segment. `thinking`, `redacted_thinking`, `tool_use` and `tool_result` blocks are now discarded (negative list, to remain tolerant of an unknown type carrying text), and a response with no text block raises an explicit error. `thinking={"type": "disabled"}` is passed on every call.

- **1.9.2** Fix news attribution URL extraction with nested parentheses or an FR prefix (2026-05-11):

  - **Bug fixed**: attribution URL extraction in `_protect_news_quotes` used the `re.search(r"\((.+?)\)", attribution)` regex (lazy capture between parentheses). For an attribution such as `(relayé par [@user sur X](https://x.com/.../123))` (nested parentheses: enclosing `(` plus the markdown link’s `]()`), capture stopped at the first `)` encountered → truncated string, also including the FR prefix: `relayé par [@user sur X](https://x.com/.../123` (without the final `)`). Consequently, `_validate_news_post` searched for this string in the translated output and failed systematically (two reasons: truncated `)` plus “relayé par” translated as `relayed by`/`weitergeleitet von`/...). The complete low → medium → high → gpt-5.5 cascade could not proceed.
  - **Fix**: the regex is now `re.search(r"\]\(([^)]+)\)", attribution)` — it specifically targets the `](url)` of the markdown link and captures **only the pure URL** (without the FR prefix or truncation), with the invariant preserved by `#URL{N}#` placeholders during translation. Robust against both problematic patterns:
    - `(relayé par [@account sur X](url))` — nested parentheses
    - `via [@source](url)` or `selon [@author](url)` — FR prefix without enclosing parentheses
  - **Tests**: 2 new tests in `test_silent_failure.py` class `TestNewsCitationExtraction`:
    - `test_extract_attribution_url_with_nested_parens` (exact reproduced case from the Genspark CEO E2B bug)
