- **1.12.0** `--use_opencode` provider: OpenCode, the open-source agent, routing to the provider of your choice — local model, free without an account, subscription, or key (2026-09-04):

  - **An eighth provider path, fundamentally different from the first seven.** [OpenCode](https://opencode.ai) (MIT) is not a model provider but a _router_ to those configured by the user within OpenCode itself: an API key, a subscription (GitHub Copilot, ChatGPT, SuperGrok), the OpenCode Zen gateway — which serves free models **without an account** — or a **local** model (Ollama, LM Studio, llama.cpp). The script drives `opencode run` in non-interactive mode, just as it drives Codex and Grok, and reuses the same subprocess foundation (dedicated process group, `SIGTERM` then `SIGKILL` on timeout, stdin always closed, sanitized environment). Verified through **two real translations**: this entire README into English via `opencode/mimo-v2.5-free` — 49 s, a single pass, structure identical to the source file (32 headings, 26 code fences, 18 links, 37 URLs, 37 table rows, 135 inline codes) — and a test file via `ollama/qwen2.5:7b`, locally, without any key.

  - **`--model provider/modèle` is mandatory, and that is intentional.** Without `--model`, OpenCode falls back to its own default, which on a fresh installation is `opencode/big-pickle`, a free “stealth” model whose exchanges may be used for training — measurements confirmed that this was the model that responded. Silently choosing that on the user's behalf would be exactly the kind of invisible switch this repository tracks; the error message therefore names the command that lists the models (`opencode models`) and gives three examples (local, free, subscription). `--eco` has no effect and says so. `--reasoning_effort` is passed through unchanged as OpenCode's `--variant`, only when explicitly requested.

  - **Measured confinement, not assumed.** An inline configuration (`OPENCODE_CONFIG_CONTENT`, last in OpenCode's merge order and therefore taking precedence over the user's configuration without replacing it) defines a `aipmt` agent for which all tools are denied (`permission: {"*": "deny"}`): the registry no longer even offers them to the model, which, when instructed to “list the files and run `id`,” replies that it has no tools. Session sharing is disabled, external plugins excluded (`--pure`), never `--auto`, disposable and empty working directory. Two silent injections were measured and disabled: without `OPENCODE_DISABLE_CLAUDE_CODE`, the user's `~/.claude/CLAUDE.md` enters **every** prompt (515 input tokens instead of 186 for a simple “Hello”); without `OPENCODE_DISABLE_PROJECT_CONFIG`, the current directory's `AGENTS.md` does too — an instruction to “end every response with BANANA” was applied to the translation. The global `~/.config/opencode/AGENTS.md`, however, remains injected: no switch excludes it, and circumventing it through a repurposed `XDG_CONFIG_HOME` would also hide the user's providers. Documented instead of patched around.

  - **`exit 0` proves nothing: third CLI, same reflexes — with two traps of its own.** An unknown `--agent` does not cause `opencode run` to fail: it emits a warning on stderr and **silently** falls back to the coding agent, with tools active. If the inline configuration were not applied, the translation would therefore run with an agent capable of writing; the output contract checks that this message is absent, in addition to: return code 0, no `error` event, no `tool_use`, final `step_finish` in `stop` (a `length` is a truncated response), non-empty text. Second trap: the JSON error event is **opaque** — “Unexpected server error. Check server logs for details.”, with only a reference — and the actual cause (`ProviderModelNotFoundError: Model not found: foo/bar. Did you mean…`, `ProviderAuthError`…) exists only in the logs. Hence `--print-logs --log-level ERROR` and reading the `error="…"` field from stderr, without the Bun stack trace that follows it. An unknown model thus fails within one second, with the cause identified. Along the way, `--title` avoids a stray LLM call: without it, OpenCode generates a session title through an additional turn on `small_model`.

  - **Secrets: the same pattern-based filtering as Codex and Grok, with one specifically named exception.** `OPENCODE_API_KEY` is retained: it is OpenCode's own key (Zen gateway, Go subscription), addressed to it by name — the equivalent of its `auth.json`, not a key that aipmt would manage or be able to bill. Providers are configured in OpenCode (`opencode auth login`, `opencode.json`), never in aipmt's `.env`, none of whose keys reach the subprocess. No refusal in CI, unlike subscription CLIs: an API key or a self-hosted model on a runner are legitimate use cases.

  - **The traversal guard now checks the interpolated value, not the raw value.** `provider/modèle` contains a `/` that the 1.10.0 guard rejected — correctly, since `--model` was interpolated into the filename `--include_model`. The filename label now replaces `/`, `\`, and `:` with `-` before any interpolation (`ollama/qwen2.5:7b` → `ollama-qwen2.5-7b`, since `:` is illegal on Windows), and the upstream guard examines this label: `../../evil` becomes the simple name `doc-en-..-..-evil.md` under the target, only `..` remains rejected, as does `--target_lang ../x`. The `_ensure_within_directory` scope guard remains the unchanged second layer.

  - **Free models and local models: what was measured.** `opencode/mimo-v2.5-free` translates one paragraph in 16 s and this README in 49 s; `opencode/big-pickle` takes 40 s for 200 words, and two simultaneous requests remained unanswered for 5 minutes even though each completes when run alone; `opencode/nemotron-3.5-lightning-free` returned nothing in 3 minutes. Hence `REGEN_PROVIDER=opencode` with mandatory `REGEN_MODEL` and **2 jobs** in parallel. Locally, Ollama often configures 4,096 context tokens while segments contain up to 16,000 characters: a `Modelfile` with `PARAMETER num_ctx 32768` is required, and quality depends on the model — a 7B model reversed a list and damaged a code-block fence in the test file, whereas the gateway model preserved everything.

  - **Translations in this repository never use a billed API anymore.** `regen_translations.sh` used the OpenAI API whenever a key happened to be present in `.env`, making Codex merely opt-in. That is exactly what happened while preparing this release: the 28 translations were sent to the OpenAI API, then the Hindi CHANGELOG to the Gemini API, even though the ChatGPT subscription exists precisely to avoid usage-based billing. Key auto-detection is removed: **Codex is the default, with `gpt-5.6-sol`**, the quality model; `openai`, `gemini`, and `grok` require `REGEN_ALLOW_PAID_API=1` in addition to `REGEN_PROVIDER`, a named exemption so that the rule takes effect at the point of decision; an unknown `REGEN_PROVIDER` fails instead of falling back to the API. Ten tests lock down the default, refusal, and exemption. The 28 translations in this release were redone through Codex.

  - **Rate-limit back-off is factored out** (`_retry_on_rate_limit`): the Codex and Grok loops were identical apart from their labels, and a third copy would have exceeded the duplication threshold. All three CLI errors derive from the same `_CliCallError`; a test prevents any of the three from leaving it, since otherwise the shared loop would no longer detect it.

  - **Tests**: new `tests/test_opencode_provider.py` file (51 tests) — complete output contract, agent fallback, cause read from logs, deduplicated text parts and ignored synthetic parts, timeout killing the process group, back-off on 429, mandatory and validated model, secret-free preflight, binary resolution, dispatch wiring, filename label, and traversal counterexample. `tests/test_review_hardening.py` extends flag exclusivity and the absence of secrets to the new provider. The gate now requires **22 documented** argparse flags. Full suite at **382 tests**.

- **1.11.0** Published on PyPI: `pip install ai-powered-markdown-translator`, then the `aipmt` command, without cloning the repository (2026-09-03):

  - **The single-file script becomes an installable package.** `translate.py` moves from the root to `src/aipmt/translate.py`, with a `aipmt` console entry point and its `python -m aipmt` equivalent. A cloned repository is still required to contribute — tests, 28 translations, and quality tooling live there — but no longer to use it.

    - **The import name is `aipmt` and never `translate`**, because the collision is real and silent. The `translate` PyPI package (v3.8.1, last uploaded 2026-07-06) installs a DIRECTORY with the same name. Reproduced in a venv: the directory takes precedence over the module, `translate.main` disappears, the entry point breaks on `AttributeError` — and `pip check` replies “No broken requirements found” with rc=0. A simple `pip install translate` on the user's system would have been enough to break the CLI without an actionable diagnostic. Counter-test on the actual wheel: `pip install translate` on top of the package, `aipmt --help` rc=0 before and after, both CLIs coexist.
    - **Long distribution name, short command.** `ai-powered-markdown-translator` makes the package discoverable through PyPI search; an acronym alone would be impossible to find for anyone who does not already know the project, while the very purpose of publishing is to be discovered. Two plausible candidates were ruled out after verification: `ai-markdown-translator` has been TAKEN on npm since 2024 by a tool with the same purpose, 17 months older than this repository; and `aimt` differs by one letter from `aim` (v3.29.1), an active package in the SAME domain — the worst setup for lasting confusion. A methodological trap along the way: `pypi.org/project/<nom>/` returns 200 for any name (anti-bot page); only the JSON API is authoritative.
    - **`src/` layout rather than a flat package.** A flat package would have preserved the six `sys.path.insert(..., "..")` statements in the tests, and that is precisely the problem: they cause the source tree to be imported instead of the package, which would hide any packaging error. Actual cost: one additional substitution rule.

  - **Keys can finally be configured once and for all.** An installed CLI had no PERSISTENT configuration: only the environment variable and the current directory's `.env` remained. `find_dotenv` admittedly searches upward to the system root and therefore found a `~/.env` **when working beneath the home directory**, but found nothing when working elsewhere — coverage that depended on where the command was launched, not on a design choice. A third layer is therefore added: `~/.config/aipmt/.env`, beneath the two existing ones.

    - **Priority is not hard-coded**; it follows from `override=False`, the default value of `load_dotenv`: each layer only fills what the previous one left empty. Hence the order environment variable → project `.env` → user configuration, verified through BEHAVIORAL rather than structural tests — reversing the order of the two calls makes them fail, as does removing the third layer.
    - **`.env` format, not TOML**, deliberately: `python-dotenv` is already a dependency, the syntax is already documented in all 15 READMEs, and the same file serves both scopes. No new dependency or syntax. The location follows `XDG_CONFIG_HOME` if it is **absolute** — the specification requires ignoring a relative value, otherwise the configuration location would again depend on the current directory — and `APPDATA` on Windows.
    - **Two options rejected, with reasons.** The system keyring (`keyring`) is safer on a desktop but fails in headless environments — server, container, CI — precisely the use case for batch translation; a good opt-in candidate, a poor default. A `--api-key` flag would put the key in shell history and expose it in `ps`.
    - **Without a key, no more call stack.** The user received a Python stack trace pointing to `site-packages`, and a message that mentioned “the environment or .env” without saying where to create the latter. It now lists all three locations with their exact paths, and the command exits with 2. The safety net is **deliberately narrow**: `except ValueError` around the configuration phase only. Wrapping the entire execution would turn a real bug occurring during translation into a reassuring message — the failure mode this repository tracks. A test reads the source of `main()` to prohibit it.

  - **Fix — the user's `.env` was ignored once the tool was installed.** `load_dotenv()` without an argument does not search upward from the current directory but from the CALLING file, therefore from `site-packages`. Measured with a real console entry point launched from a project with its own `.env`: `find_dotenv()` returns `''` and the key is not loaded, whereas `find_dotenv(usecwd=True)` finds it. The bug did not exist while the tool ran only from the cloned repository; publishing would have made it systematic, with an API key reported as “missing” despite a correct configuration as its only symptom.

  - **Three gates would have turned green after ceasing to verify anything.** They were hardened BEFORE the move, deliberately: a safeguard written after the change it is supposed to catch proves nothing. Each is green on the original repository and turns red on a migrated copy — both directions were measured.
    - **Lizard silently ignores a missing path**: rc=0, “0 file analyzed.” The complexity gate would have gone from 158 functions / 2247 nloc to 3 functions / 34 nloc, with zero-byte output. The scope is now an array in which every entry is checked for existence.
    - **`coverage run --source=` on a missing module does not fail**: warning on stderr only, rc=0 for both unittest and `coverage xml`, with the report still published—cut from 1453 to 141 statements. The project would have appeared healthy because it was barely being analyzed anymore. Two floors now safeguard the report: the total and the largest measured file.
    - **The translation freshness probe is structurally blind to the invocation form**: it anchors on the argparse flags, precisely what a file rename does not change. Reproduced: module moved, all 15 READMEs still documenting a nonexistent command, verdict “no stale translations.” A 7th section therefore checks the FORM rather than the options, and the Lizard hook is compared against the script’s actual scope—its `files:` key does not make pre-commit fail when it no longer matches; it makes it SKIP.

  - **`requires-python = ">=3.10"` is no longer merely an assertion.** `sonar-project.properties` already advertised 3.10–3.12 even though nothing had ever exercised them, since the development machine only had 3.12—an internal contradiction that publication would have made public. A test workflow now runs the suite on 3.10, 3.11, and 3.12, installing the PACKAGE and therefore enforcing its public bounds.

  - **Lower bounds, no upper bound.** `requirements.txt` remains the tested lock, while `[project.dependencies]` becomes the public contract: publishing the lock’s exact versions would cause conflicts for any user with other packages. No `<N+1` upper bound either—it would directly contradict `check-deps-fresh.sh`, which makes the release gate fail on any major-version lag. The set of floors solves this, and the counter-test `openai==1.0.0` exits with `ResolutionImpossible`, proving that the check discriminates instead of accepting everything. A guard also prevents the version in `pyproject.toml` from diverging from the CHANGELOG version: PyPI does not allow a version number to be reused.

  - **Verified end to end in a fresh venv**: a wheel of about 70 KB containing only `aipmt/*.py`, the dist-info, and the license; `aipmt --help` rc=0 with 22 flags; `python -m aipmt` displaying “usage: aipmt” rather than “usage: \_\_main\_\_.py”; working `pipx` installation; and, most importantly, **a real fr→en translation from any user directory**, with bold text, a list, inline code, a link, and a URL preserved, and the code block left untranslated. The 318 tests that predated the migration pass with a list of identifiers identical byte for byte before and after—that is what proves that no test was disabled, not the “OK”; twelve more cover the three-layer configuration, for a total of 330.

- **1.10.0** `--use_codex` provider (ChatGPT subscription quota), SDK and model updates, fix for multi-paragraph news citations (2026-08-29):

  - **Security review—two safeguards that the PR established without enforcing them everywhere**:

    - **The Codex preflight passed the entire `.env` to the binary.** `_codex_preflight` called `subprocess.run` **without `env=`**: the subprocess inherited all of `os.environ`, including the entirety of `.env` loaded by `load_dotenv`. Measured with an instrumented fake binary: **seven secrets** reached the preflight—the keys for all six providers plus one `GITHUB_TOKEN`—versus **zero** for its `_grok_preflight` counterpart, which did pass `env=_grok_env()`. The inconsistency was internal to the PR: `_strip_secret_env` exists precisely to uphold this invariant, only a few lines away. A `_codex_env_base()` is extracted and shared by both paths; measurement after the fix: 0 secrets on either side.
    - **The “`--deny` fail-closed” property did not cover the form being used.** The comment justified the entire Grok confinement approach on the grounds that a rule with an unknown prefix prevents startup. Measured on `grok 1.0.13`, this validation exists **only for the parenthesized form**: `--deny 'CeciNestPasUnOutil(*)'` refuses to start (“unknown tool prefix”), while `--deny 'CeciNestPasUnOutil'` is silently accepted. Yet `GROK_DENY_RULES` used only bare names—renaming a tool on the xAI side would therefore have removed the only measured confinement layer without any signal, on a machine where the OS sandbox already does not apply. The eight named rules switch to `Prefix(*)`, each verified by the CLI as a known prefix; the catch-all `*` remains in its literal form, the only accepted one. A test prevents regression to the unvalidated form.
    - **Otherwise verified clean**: no command injection (list form throughout, never `shell=True`, document content via stdin or `--prompt-file`), no unsafe deserialization (`json.loads` only, with a type guard), no bypass found for the path traversal fix across seven payloads, and `--deny '*'` actually enforced by the CLI (`DENY_ENFORCED` observed on a read outside the workdir).
    - The freshness check added above also circumvented its own principle: a package whose PyPI request failed was silently skipped, leaving the gate green. It now counts the packages actually compared and fails if coverage is incomplete.

  - **Dependencies brought up to date, with two safety nets to prevent the lag from recurring**:

    - **The lag was real and persistent**: `openai` 2.54 → **3.6.0**, `anthropic` 0.125 → **1.2.0**, `certifi` 2024.8.30 → **2026.7.22**—a two-year lag in the root certificate store that validates TLS for every provider call. Root cause identified: **there was no `.github/dependabot.yml`**. Without this file, GitHub enables only _security updates_, and Dependabot opens a PR only for a dependency affected by a CVE—which explains why it bumped `urllib3` and `idna` while allowing two SDKs to drift by a major version.
    - **The two major versions coexist without conflict**, contrary to what earlier reasoning had suggested: `openai` 3.x and `anthropic` 1.x migrate to **`httpx2`**, while `mistralai` and `google-genai` remain on `httpx<1`, but these are two distinct distributions. Verified through an actual installation, then through **all 7 provider paths tested end to end**—OpenAI, Claude, Mistral, Gemini, Grok API, Codex CLI, and Grok CLI—with inline code and links preserved in every output. “Avoid two HTTP stacks” was a preference, not a blocker: the measurement settled the matter.
    - **`requirements.txt` did not describe the actual environment**: `google-auth`, `cryptography`, and the `opentelemetry` stack were installed in the working venv without ever being declared—a fresh installation therefore did not reproduce what was being tested. Conversely, `tokenizers`, `huggingface-hub`, and `PyYAML` were listed there without being imported or required by anything, remnants of `mistralai` 1.x. The file is regenerated as the complete closure of a venv built solely from the direct dependencies. `pip-audit` reports no known vulnerabilities in the new set.
    - **`.github/dependabot.yml`** (new) enables weekly version updates for pip and github-actions. Minor and patch updates are grouped into a single PR—a separate PR for every patch bump eventually gets ignored, and noise is the enemy of maintenance; **major updates are separate**, each requiring validation through a real call.
    - **`scripts/check-deps-fresh.sh`** (new, wired into the gate) makes lag visible in the project verdict: Dependabot proposes updates; it does not guarantee them, and its PRs can pile up. Major-version lag → failure; minor-version lag → warning, because a permanently red gate eventually gets ignored; PyPI unreachable → explicit skip locally and **fail-closed in CI**, since a check that did not run is not a success. Verified in both directions: it catches the exact pre-fix state (`openai 2.54.0→3.6.0`, `certifi 2024.8.30→2026.7.22`) and merely warns on a minor-version lag.

  - **Fixes arising from the review of this PR**—five review agents scrutinized the diff; every issue below was **reproduced through measurement** before being fixed, and two of them were regressions introduced earlier in this same version.
    - **Fixed regression — `_NEWS_CITATION_REGEX` had exponential backtracking.** The multi-paragraph fix had introduced `(?:[ \t]*$|[ \t]+.*)` into the repetition: the distribution of spaces between `[ \t]+` and `.*` is ambiguous, and this ambiguity multiplies from one iteration to the next. Measured on `>   texte` lines — perfectly valid Markdown indentation — that do not match the pattern: **2,589 ms for 14 lines** versus 0.04 ms after the fix, with a factor of ~9 per additional line. In `--news` mode, a long, non-compliant blockquote was enough to freeze translation until the job timed out, with no identifiable cause. The repetition now consumes the entire line in one go (`\n^>(?![ \t]*—).*`), leaving only one way to match each iteration. Verified on the real corpus of 231 articles: **zero difference** in captures, the same 423 quotations, and all 14 multi-paragraph bodies still extended.
    - **Two simultaneous provider flags silently incurred usage-based billing.** `--use_codex --use_mistral` was accepted; `_select_provider_client` checks Mistral first, while `_resolve_provider` prioritizes explicit booleans — both converged on Mistral. The user was therefore requesting their subscription quota and receiving usage-based billing without any warning: exactly the failure mode `--use_codex` exists to prevent. All six provider flags now go through a `add_mutually_exclusive_group`. **Behavioral change**: a command line combining two providers, previously accepted silently, now fails on `argument --use_mistral: not allowed with argument --use_codex`.
    - **The completion gate turned green when its probes crashed.** Four of the thirteen `scripts/check-release-ready.sh` checks followed the “capture stdout, conclude if empty” pattern without ever checking the exit code: an exception (renamed file, `FileNotFoundError`) wrote to stderr, left stdout empty, and the check concluded “nothing to report.” The “an `exit 0` proves nothing” trap was reproduced inside the script written to prevent it. A `probe()` helper now requires both a zero exit code **and** an end sentinel, and the probes refuse to draw conclusions from an empty set of markers — an assertion over an empty set is always true. Demonstration: adding the exclusive group above routed the provider flags through an `*_group` object, which the old `parser\.add_argument\(` regex no longer matched; **six flags out of twenty-one** silently fell outside the scope, with the gate still green.
    - **The secret scan missed four out of six providers.** The `[A-Za-z0-9]` class excludes hyphens: `sk-proj-…` (the current OpenAI format) and `sk-ant-api03-…` broke at their second hyphen, and `AIza…` was not covered. The pattern was expanded, and `.secrets.baseline` was excluded from the scan. The `.env` guard also queried `git diff --cached`, which only sees the index: an `.env` **already committed** — the worst case — never appeared there. It now queries `git ls-files`.
    - **The Codex “token warm-up” was not a warm-up.** Measured: `codex login status` does not touch `~/.codex/auth.json` (mtime and size unchanged), and its help text says “Show login status.” Yet the comment claimed it refreshed the token “once, sequentially,” thereby eliminating the risk of concurrent refreshes on a rotating single-use token. The advertised protection did not exist; the comment now states what the code actually does, and the real mitigation remains `max_jobs=4`. The check also now honors `CODEX_BIN`, which it previously ignored — a machine without `codex` in `PATH` failed with “not authenticated,” a misleading diagnosis.
    - **`.env` was sourced in a subshell.** `detect_provider` is called through command substitution, so its exports did not propagate: an `GROK_BIN`, `GROK_HOME`, or `REGEN_MODEL` defined in `.env` remained invisible to reads performed in `main()`, which concluded “Grok binary not found” despite a correct configuration.
    - **Concurrency exceeded the advertised limit by 50%.** The guard was placed after launching the README/CHANGELOG pair: the measured peak was **3 for `max_jobs=2`**. For Grok, whose weekly quota is shared with Chat/Imagine/Voice and cannot be measured, the limit imposed by the script was therefore not respected. The final count, meanwhile, was displayed without ever being compared with 28 — a missing file went unnoticed.
    - **Grok output contract: a missing `stopReason` is now a failure.** The code applied “`end_turn` **or absent**” where the documented contract requires `end_turn`. A payload without the field — or with the field renamed by a CLI update — turned the guard into a silent no-op. In addition, `max_turn_requests` is no longer classified as a rate limit (the turn budget has been exhausted: retrying reproduces the result at the cost of a 90-second wait), and `quota` has been removed from the rate-limit markers — for the reason already stated in the `_codex_is_rate_limited` docstring but not applied by Grok.
    - **The Gemini fallback chain is memoized by model.** It restarted from `minimal` for every segment, even though the default model rejects it: the nominal path paid for a 400 round trip per segment and printed the same warning again. A warning repeated hundreds of times stops being read — that is how it becomes a mask.
    - **Miscellaneous**: the CI refusal message was hard-coded for Codex and directed a `--use_grok_cli` user to `OPENAI_API_KEY` instead of `XAI_API_KEY`; `provider.capitalize()` displayed “Grok_cli” and “Openai”; the subprocess foundation comment generalized the “shim” to both CLIs even though the Grok binary is a native ELF (the correct rationale is “agent that spawns its own subprocesses”); twelve SAST findings on `subprocess` are marked `# nosec` / `# nosemgrep` with justification, since the list form without `shell=True` makes injection impossible and the document content never passes through argv.
    - **No secrets enter agentic subprocesses anymore.** Named deny-lists protected only the **billing** invariant (Codex without `OPENAI_API_KEY`, Grok without `XAI_API_KEY`). Measured: **seven other secrets** still entered every subprocess — the Anthropic, Mistral, Google, and Gemini keys, the other CLI's key, and `OPENAI_BASE_URL`, which is not a secret but redirects traffic. Yet both CLIs are **agents**, and the Grok one runs without an applicable OS sandbox on many Linux machines. Filtering is now performed **by name pattern** (`API_KEY`, `_TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIALS`) rather than by a named list, which also covers variables users add to their `.env` without this code knowing about them. None are required by the CLIs: authentication lives in `~/.codex` and `~/.grok`, never in the environment — verified through a **successful real translation** using each provider with the hardened environment.
    - **Tests**: new `tests/test_review_hardening.py` file (21 tests) locking down provider-flag exclusivity, the `stopReason` contract, the linear behavior of the news regex, the CI refusal message, Gemini memoization, and the absence of all secrets from the subprocess environment. The latter assertion is **generic** — it fails on a key not named by any list — whereas the existing scrubbing test mirrored its constant and could detect nothing beyond a failure in its own loop. Full suite now at **311 tests**.

  - **Two new Grok providers**: `--use_grok` (xAI API, `XAI_API_KEY` key, usage-based billing) and `--use_grok_cli` (official Grok Build CLI, counted against the Grok subscription — the same principle as `--use_codex`).
    - **API mode, ~40 lines**: since the xAI endpoint is OpenAI-compatible, the client and `_call_openai` are reused as-is; only the `base_url` changes. Only one adaptation was necessary, and it benefits everyone: `finish_reason` now accepts `end_turn`, the form emitted by xAI where OpenAI emits `stop`. Models: `grok-4.6` (quality) and `grok-4.3` (economy). Note that Grok's economy model remains the most expensive in the repository — $1.25/$2.50 per million versus $0.15/$0.60 for `mistral-small-latest`: this provider is chosen for model diversity, not price.

The central trap: a **built-in** profile that cannot be applied **starts silently without confinement**. The script therefore requests no profile by default and never falls back silently — it warns on stderr. Protection relies on the CLI's `--deny` rules, including the `*` catch-all, the only layer measured to be _fail-closed_ (a rule with an unknown prefix prevents startup). `GROK_TRANSLATE_SANDBOX=read-only` allows confinement to be required, in which case startup fails if the machine cannot honor it.

- **1.9.2** Fix news attribution URL extraction with nested parentheses or an FR prefix (2026-05-11):
