- **1.11.0** Publicação no PyPI: `pip install ai-powered-markdown-translator` e depois o comando `aipmt`, sem clonar o repositório (2026-09-03) :

  - **O script de arquivo único torna-se um pacote instalável.** `translate.py` passa da raiz para `src/aipmt/translate.py`, com um ponto de entrada de console `aipmt` e o equivalente `python -m aipmt`. O repositório clonado continua necessário para contribuir — testes, 28 traduções e ferramentas de qualidade vivem nele — mas não mais para usar.

    - **O nome de importação é `aipmt` e nunca `translate`**, porque a colisão é real e silenciosa. O pacote PyPI `translate` (v3.8.1, último upload em 2026-07-06) instala um DIRETÓRIO com o mesmo nome. Reproduzido em um venv: o diretório prevalece sobre o módulo, `translate.main` desaparece, o ponto de entrada falha em `AttributeError` — e `pip check` responde « No broken requirements found » com rc=0. Um simples `pip install translate` no ambiente do usuário teria bastado para quebrar a CLI sem diagnóstico útil. Contraprova no wheel real: `pip install translate` sobre o pacote, `aipmt --help` rc=0 antes e depois, as duas CLIs coexistem.
    - **Nome de distribuição longo, comando curto.** `ai-powered-markdown-translator` torna o pacote localizável por uma pesquisa no PyPI; um acrônimo sozinho seria impossível de encontrar para quem já não conhece o projeto, quando a publicação visa precisamente ser encontrada. Dois candidatos plausíveis foram descartados por verificação: `ai-markdown-translator` está OCUPADO no npm desde 2024 por uma ferramenta com o mesmo objetivo, anterior a este repositório em 17 meses; e `aimt` difere por uma letra de `aim` (v3.29.1), pacote ativo do MESMO domínio — a pior configuração para uma confusão duradoura. Armadilha metodológica adicional: `pypi.org/project/<nom>/` retorna 200 para qualquer nome (página anti-bot); apenas a API JSON é confiável.
    - **Layout `src/` em vez de pacote plano.** O pacote plano teria preservado os seis `sys.path.insert(..., "..")` dos testes, e esse é precisamente o problema: eles fazem importar a árvore de origem em vez do pacote, mascarando qualquer erro de empacotamento. Custo real: uma regra de substituição adicional.

  - **As chaves finalmente são configuradas de uma vez por todas.** Uma CLI instalada não tinha nenhuma configuração PERSISTENTE: restavam a variável de ambiente e o `.env` do diretório atual. `find_dotenv` de fato subia até a raiz do sistema e encontrava um `~/.env` **quando se trabalhava dentro do próprio diretório pessoal**, mas nada quando se trabalhava em outro lugar — uma cobertura que dependia do local de onde o comando era executado, não de uma escolha de design. Portanto, acrescenta-se uma terceira camada: `~/.config/aipmt/.env`, abaixo das duas existentes.

    - **A prioridade não é codificada**, ela decorre de `override=False`, valor padrão de `load_dotenv`: cada camada preenche apenas o que a anterior deixou vazio. Daí a ordem variável de ambiente → `.env` do projeto → configuração do usuário, verificada por testes de COMPORTAMENTO e não de estrutura — inverter a ordem das duas chamadas faz os testes falharem, assim como remover a terceira camada.
    - **Formato `.env` e não TOML**, deliberadamente: `python-dotenv` já é uma dependência, a sintaxe já está documentada nos 15 README, e o mesmo arquivo serve aos dois escopos. Nenhuma dependência nem sintaxe nova. O local segue `XDG_CONFIG_HOME` se for **absoluto** — a especificação exige ignorar um valor relativo, caso contrário o local da configuração voltaria a depender do diretório atual — e `APPDATA` no Windows.
    - **Duas opções descartadas, com seus motivos.** O chaveiro do sistema (`keyring`) é mais seguro em um computador de mesa, mas falha em headless — servidor, contêiner, CI — exatamente o caso de uso de uma tradução em lote; bom candidato para opt-in, péssimo padrão. Um flag `--api-key` faria a chave parar no histórico do shell e a tornaria visível em `ps`.
    - **Sem chave, não há mais rastreamento da chamada.** O usuário recebia uma pilha Python apontando para `site-packages` e uma mensagem que mencionava « o ambiente ou .env » sem dizer onde criar o segundo. Agora enumera os três locais com seus caminhos exatos, e o comando termina com 2. A proteção é **deliberadamente estreita**: `except ValueError` apenas na fase de configuração. Envolver toda a execução transformaria um bug real ocorrido durante a tradução em uma mensagem tranquilizadora — o modo de falha que este repositório busca detectar. Um teste lê o código-fonte de `main()` para proibir isso.

  - **Correção — o `.env` do usuário era ignorado depois que a ferramenta era instalada.** `load_dotenv()` sem argumento não sobe a partir do diretório atual, mas a partir do arquivo CHAMADOR, ou seja, de `site-packages`. Medido com um ponto de entrada de console real executado a partir de um projeto que possui seu próprio `.env`: `find_dotenv()` retorna `''` e a chave não é carregada, enquanto `find_dotenv(usecwd=True)` a encontra. O bug não existia enquanto a ferramenta era executada apenas a partir do repositório clonado; a publicação o teria tornado sistemático, com o único sintoma de uma chave de API « ausente » em uma configuração correta.

  - **Três gates teriam passado para verde depois de deixar de verificar qualquer coisa.** Eles foram reforçados ANTES da movimentação, deliberadamente: uma proteção escrita depois da alteração que deveria detectar não prova nada. Cada um fica verde no repositório original e vermelho em uma cópia migrada — ambas as direções são medidas.

    - **O Lizard ignora um caminho ausente sem dizer nada**: rc=0, « 0 file analyzed ». O gate de complexidade teria passado de 158 funções / 2247 nloc para 3 funções / 34 nloc, com uma saída de zero bytes. O escopo agora é uma matriz cuja existência de cada entrada é verificada.
    - **`coverage run --source=` em um módulo ausente não falha**: aviso apenas em stderr, rc=0 tanto para unittest quanto para `coverage xml`, e relatório publicado mesmo assim — reduzido de 1453 para 141 statements. O projeto teria parecido saudável porque quase não era mais analisado. Dois limites mantêm o relatório: o total e o maior arquivo medido.
    - **A sonda de atualidade das traduções é estruturalmente cega à forma de invocação**: ela se ancora nos flags do argparse, precisamente aquilo que uma renomeação de arquivo não altera. Reproduzido: módulo movido, os 15 README ainda documentando um comando inexistente, veredito « nenhuma tradução desatualizada ». Portanto, uma 7ª seção verifica a FORMA, e não as opções, e o hook do Lizard é confrontado com o escopo real do script — sua chave `files:` não faz o pre-commit falhar quando deixa de corresponder; ela o FAZ PULAR.

  - **`requires-python = ">=3.10"` deixa de ser uma afirmação.** `sonar-project.properties` já anunciava 3.10-3.12 sem que isso jamais tivesse sido exercitado, pois o ambiente de desenvolvimento tinha apenas 3.12 — uma contradição interna que a publicação teria tornado pública. Um workflow de testes agora executa a suíte em 3.10, 3.11 e 3.12, instalando o PACOTE e, portanto, seus limites públicos.

  - **Limites inferiores, nenhum teto.** `requirements.txt` continua sendo o lock testado, `[project.dependencies]` torna-se o contrato público: publicar as versões exatas do lock provocaria conflitos para qualquer usuário com outros pacotes. Também não há teto `<N+1` — ele entraria em contradição frontal com `check-deps-fresh.sh`, que faz o gate de release falhar em qualquer atraso de major. O conjunto de limites inferiores resolve isso, e a contraprova `openai==1.0.0` termina em `ResolutionImpossible`, provando que o controle discrimina em vez de aceitar tudo. Além disso, uma proteção impede que a versão de `pyproject.toml` divirja da versão do CHANGELOG: o PyPI não permite reutilizar um número.

  - **Verificado de ponta a ponta em um venv novo**: wheel de aproximadamente 70 KB contendo apenas `aipmt/*.py`, o dist-info e a licença; `aipmt --help` rc=0 com 22 flags; `python -m aipmt` exibindo « usage: aipmt » e não « usage: \_\_main\_\_.py »; instalação `pipx` funcional; e, sobretudo, **uma tradução real fr→en a partir de qualquer diretório do usuário**, com negrito, lista, código inline, link e URL preservados, e bloco de código não traduzido. Os 318 testes anteriores à migração passam com uma lista de identificadores idêntica byte a byte antes/depois — é isso que prova que nenhum teste foi neutralizado, não o « OK »; doze são acrescentados para a configuração em três camadas, totalizando 330.

- **1.10.0** Provider `--use_codex` (cota de assinatura do ChatGPT), atualização dos SDKs e dos modelos, correção das citações de notícias em múltiplos parágrafos (2026-08-29) :

  - **Revisão de segurança — duas proteções que a PR instalava sem mantê-las em todos os lugares** :

    - **O preflight do Codex transmitia todo o `.env` ao binário.** `_codex_preflight` chamava `subprocess.run` **sem `env=`**: o subprocesso herdava o `os.environ` completo, portanto a totalidade do `.env` carregado por `load_dotenv`. Medido com um binário falso instrumentado: **sete segredos** chegavam ao preflight — as chaves dos seis providers mais um `GITHUB_TOKEN` — contra **zero** para seu equivalente `_grok_preflight`, que passava corretamente `env=_grok_env()`. A inconsistência era interna à PR: `_strip_secret_env` existe precisamente para manter esse invariante, a poucas linhas dali. Um `_codex_env_base()` é extraído e compartilhado pelos dois caminhos; medição após a correção: 0 segredos de ambos os lados.
    - **A propriedade « `--deny` fail-closed » não cobria a forma utilizada.** O comentário justificava todo o confinamento do Grok pelo fato de que uma regra com prefixo desconhecido faz a inicialização ser recusada. Medido em `grok 1.0.13`, essa validação existe **apenas para a forma entre parênteses**: `--deny 'CeciNestPasUnOutil(*)'` recusa a inicialização (« unknown tool prefix »), enquanto `--deny 'CeciNestPasUnOutil'` é aceito silenciosamente. Ora, `GROK_DENY_RULES` usava apenas nomes sem adornos — uma renomeação de ferramenta no lado da xAI teria removido a única camada de confinamento medida sem o menor sinal, em uma máquina onde o sandbox do SO já não se aplica. As oito regras nomeadas passam em `Prefix(*)`, cada uma verificada como prefixo conhecido da CLI; o catch-all `*` permanece em sua forma literal, a única aceita. Um teste impede o retorno à forma não validada.
    - **Verificado corretamente nos demais pontos**: nenhuma injeção de comando (forma de lista em todos os lugares, nunca `shell=True`, conteúdo do documento via stdin ou `--prompt-file`), nenhuma desserialização insegura (`json.loads` apenas, com verificação de tipo), correção da travessia de caminho sem desvio encontrado em sete cargas úteis, e `--deny '*'` efetivamente aplicado pela CLI (`DENY_ENFORCED` observado em uma leitura fora do workdir).
    - O controle de atualidade adicionado acima também contornava seu próprio princípio: um pacote cuja requisição ao PyPI falhava era ignorado silenciosamente, deixando o gate verde. Agora ele contabiliza os pacotes realmente comparados e falha se a cobertura estiver incompleta.

  - **Dependências atualizadas, e duas redes para evitar que o atraso se repita** :

    - **O atraso era real e duradouro**: `openai` 2.54 → **3.6.0**, `anthropic` 0.125 → **1.2.0**, `certifi` 2024.8.30 → **2026.7.22** — dois anos de atraso no armazenamento de certificados-raiz que valida TLS para todas as chamadas dos providers. Causa identificada: **não existia um `.github/dependabot.yml`**. Sem esse arquivo, o GitHub ativa apenas as _security updates_, e o Dependabot só propõe uma PR para uma dependência afetada por uma CVE — o que explica ter atualizado `urllib3` e `idna` enquanto deixava dois SDKs se afastarem de uma versão major.
    - **As duas versões major coexistem sem conflito**, ao contrário do que um raciocínio anterior fazia temer: `openai` 3.x e `anthropic` 1.x migram para **`httpx2`** quando `mistralai` e `google-genai` permanecem em `httpx<1`, mas são duas distribuições distintas. Verificado por instalação real e depois pelos **7 caminhos de provider testados de ponta a ponta** — OpenAI, Claude, Mistral, Gemini, Grok API, Codex CLI e Grok CLI — com código inline e links preservados em cada saída. « Evitar duas pilhas HTTP » era uma preferência, não um bloqueio: a medição decidiu.
    - **`requirements.txt` não descrevia o ambiente real**: `google-auth`, `cryptography` e a pilha `opentelemetry` estavam instalados no venv de trabalho sem jamais serem declarados — uma instalação nova, portanto, não reproduzia o que era testado. Por outro lado, `tokenizers`, `huggingface-hub` e `PyYAML` apareciam nele sem serem importados nem exigidos por nada, resquícios de `mistralai` 1.x. O arquivo é regenerado como o fechamento completo de um venv construído apenas a partir das dependências diretas. `pip-audit` não aponta nenhuma vulnerabilidade conhecida no novo conjunto.
    - **`.github/dependabot.yml`** (novo) ativa atualizações semanais de versão, pip e github-actions. Versões minor e correções agrupadas em uma PR — um patch bump por PR acaba ignorado, e o ruído é inimigo da atualização; **majors separadas**, cada uma exigindo validação por chamada real.
    - **`scripts/check-deps-fresh.sh`** (novo, conectado ao gate) torna o atraso visível no veredito do projeto: o Dependabot propõe, não garante, e suas PRs podem se acumular. Atraso de major → falha; minor → aviso, porque um gate permanentemente vermelho acaba sendo ignorado; PyPI inacessível → skip explícito localmente e **fail-closed na CI**, pois um controle não executado não é um sucesso. Verificado nos dois sentidos: ele captura exatamente o estado anterior à correção (`openai 2.54.0→3.6.0`, `certifi 2024.8.30→2026.7.22`) e limita-se a avisar sobre uma minor.

  - **Correções decorrentes da revisão desta PR** — cinco agentes de revisão examinaram o diff minuciosamente; todos os pontos abaixo foram **reproduzidos por medição** antes da correção, e dois deles eram regressões introduzidas anteriormente nesta mesma versão.
- **Regressão corrigida — `_NEWS_CITATION_REGEX` tinha backtracking exponencial.** A correção para múltiplos parágrafos havia introduzido `(?:[ \t]*$|[ \t]+.*)` na repetição: o compartilhamento dos espaços entre `[ \t]+` e `.*` é ambíguo, e essa ambiguidade se multiplica de uma iteração para outra. Medido em linhas `>   texte` — indentação Markdown perfeitamente válida — que não correspondem ao padrão: **2 589 ms para 14 linhas** contra 0,04 ms após a correção, com um fator de ~9 por linha adicionada. No modo `--news`, um blockquote longo e não conforme bastava para congelar a tradução até o timeout do job, sem causa identificável. A repetição agora consome a linha inteira de uma só vez (`\n^>(?![ \t]*—).*`), deixando apenas uma forma de corresponder por iteração. Verificado no corpus real de 231 artigos: **zero diferenças** de captura, as mesmas 423 citações, e os 14 corpos com múltiplos parágrafos continuam sendo expandidos.
    - **Dois flags de provider simultâneos geravam cobrança por uso, silenciosamente.** `--use_codex --use_mistral` era aceito; `_select_provider_client` testa Mistral primeiro, `_resolve_provider` dá prioridade aos booleanos explícitos — ambos convergiam para Mistral. Assim, o usuário solicitava sua cota de assinatura e obtinha cobrança por uso, sem o menor aviso: exatamente o modo de falha que `--use_codex` existe para impedir. Os seis flags de provider agora passam por um `add_mutually_exclusive_group`. **Mudança de comportamento**: uma linha de comando combinando dois providers, antes aceita silenciosamente, agora falha em `argument --use_mistral: not allowed with argument --use_codex`.
    - **O gate de fim de trabalho ficava verde quando suas sondas falhavam.** Quatro das treze verificações de `scripts/check-release-ready.sh` seguiam o padrão “capturar stdout, concluir se vazio” sem nunca consultar o código de retorno: uma exceção (arquivo renomeado, `FileNotFoundError`) escrevia em stderr, deixava stdout vazio, e a verificação concluía “nada a sinalizar”. A armadilha “um `exit 0` não prova nada” foi reproduzida dentro do script criado para impedi-la. Um helper `probe()` agora exige código de retorno nulo **e** sentinela de fim, e as sondas se recusam a concluir com base em um conjunto vazio de marcadores — uma asserção sobre conjunto vazio é sempre verdadeira. Demonstração: a adição do grupo exclusivo acima fez os flags de provider passarem por um objeto `*_group`, que a regex antiga `parser\.add_argument\(` já não correspondia; **seis flags de vinte e um** saíam silenciosamente do escopo, com o gate verde.
    - **O scan de secrets não detectava quatro providers de seis.** A classe `[A-Za-z0-9]` exclui o hífen: `sk-proj-…` (formato OpenAI atual) e `sk-ant-api03-…` falhavam no segundo hífen, e `AIza…` não era coberto. Padrão ampliado, `.secrets.baseline` excluído do scan. Além disso, a proteção `.env` consultava `git diff --cached`, que vê apenas o índice: um `.env` **já commitado** — o pior caso — nunca aparecia ali. Agora ela consulta `git ls-files`.
    - **O “aquecimento do token” do Codex não era um aquecimento.** Medido: `codex login status` não toca em `~/.codex/auth.json` (mtime e tamanho inalterados), e sua ajuda diz “Show login status”. O comentário, porém, afirmava atualizar o token “uma vez, sequencialmente”, neutralizando assim o risco de refresh concorrentes em um token rotativo de uso único. A proteção anunciada não existia; o comentário agora descreve o que o código faz, e a proteção real continua sendo `max_jobs=4`. O controle também respeita `CODEX_BIN`, que ignorava — uma máquina sem `codex` no `PATH` falhava com “não autenticado”, um diagnóstico enganoso.
    - **`.env` era carregado em um subshell.** `detect_provider` é chamada em uma substituição de comando, portanto suas exportações não subiam: um `GROK_BIN`, `GROK_HOME` ou `REGEN_MODEL` definido em `.env` permanecia invisível para as leituras feitas em `main()`, que concluía “binário Grok não encontrado” em uma configuração correta.
    - **A concorrência excedia em 50% o limite anunciado.** A proteção estava posicionada depois do lançamento do par README/CHANGELOG: pico medido de **3 para `max_jobs=2`**. No Grok, cuja cota semanal é compartilhada com Chat/Imagine/Voice e não pode ser medida, o limite imposto pelo script não era, portanto, respeitado. A contagem final, por sua vez, era exibida sem nunca ser comparada a 28 — um arquivo ausente passava despercebido.
    - **Contrato de saída do Grok: um `stopReason` ausente agora é uma falha.** O código aplicava “`end_turn` **ou ausente**” onde o contrato anunciado exige `end_turn`. Um payload sem o campo — ou cujo campo fosse renomeado por uma atualização do CLI — transformava a proteção em um no-op silencioso. Além disso, `max_turn_requests` já não é classificado como rate limit (é o orçamento de turnos que se esgotou: tentar novamente reproduz o resultado, ao custo de 90 s de espera), e `quota` deixa de emitir marcadores de rate limit — pelo motivo que o docstring de `_codex_is_rate_limited` já explicava, sem que o Grok o aplicasse.
    - **A cascata Gemini agora é memorizada por modelo.** Ela recomeçava em `minimal` a cada segmento, embora o modelo padrão o recuse: o caminho nominal pagava uma ida e volta 400 por segmento e imprimia novamente o mesmo aviso. Um warning repetido centenas de vezes deixa de ser lido — é assim que ele se torna uma máscara.
    - **Diversos**: a mensagem de recusa em CI estava codificada para o Codex e encaminhava um usuário de `--use_grok_cli` para `OPENAI_API_KEY` em vez de `XAI_API_KEY`; `provider.capitalize()` exibia “Grok_cli” e “Openai”; o comentário da base de subprocessos generalizava o “shim” para os dois CLIs, embora o binário Grok seja um ELF nativo (a justificativa correta é “agente que gera seus próprios subprocessos”); doze findings SAST em `subprocess` foram marcados como `# nosec` / `# nosemgrep` com justificativa, sendo que a forma de lista sem `shell=True` torna a injeção impossível e o conteúdo do documento nunca transita por argv.
    - **Nenhum secret entra mais nos subprocessos agentic.** As deny-lists nominais protegiam apenas o invariante de **cobrança** (Codex sem `OPENAI_API_KEY`, Grok sem `XAI_API_KEY`). Medido: **sete outros secrets** ainda entravam em cada subprocesso — as chaves Anthropic, Mistral, Google e Gemini, a do outro CLI e `OPENAI_BASE_URL`, que não é um secret, mas redireciona o tráfego. Ora, esses dois CLIs são **agentes**, e o do Grok roda sem sandbox do SO aplicável em muitas máquinas Linux. O filtragem agora é feita **por padrão de nome** (`API_KEY`, `_TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIALS`), e não por lista nominal, cobrindo também as variáveis que um usuário adiciona ao seu `.env` sem que esse código as conheça. Nenhuma é necessária para os CLIs: a autenticação reside em `~/.codex` e `~/.grok`, nunca no ambiente — verificado por uma **tradução real concluída** através de cada um dos dois providers com o ambiente reforçado.
    - **Testes**: novo arquivo `tests/test_review_hardening.py` (21 testes), garantindo a exclusividade dos flags de provider, o contrato `stopReason`, a linearidade da regex news, a mensagem de recusa em CI, a memorização do Gemini e a ausência de qualquer secret no ambiente dos subprocessos. Esta última asserção é **genérica** — falha diante de uma chave que nenhuma lista nomeia — enquanto o teste de expurgo existente era um espelho de sua constante e não podia detectar nada além da falha de seu próprio loop. Suíte completa com **311 testes**.
