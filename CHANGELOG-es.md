- **1.11.0** Publicación en PyPI: `pip install ai-powered-markdown-translator` y luego el comando `aipmt`, sin clonar el repositorio (2026-08-31):

  - **El script de un solo archivo se convierte en un paquete instalable.** `translate.py` pasa de la raíz a `src/aipmt/translate.py`, con un punto de entrada de consola `aipmt` y su equivalente `python -m aipmt`. El repositorio clonado sigue siendo necesario para contribuir —allí viven las pruebas, 28 traducciones y las herramientas de calidad—, pero ya no para utilizarlo.

    - **El nombre de importación es `aipmt` y nunca `translate`**, porque la colisión es real y silenciosa. El paquete de PyPI `translate` (v3.8.1, última carga el 2026-07-06) instala un DIRECTORIO con el mismo nombre. Reproducido en un venv: el directorio prevalece sobre el módulo, `translate.main` desaparece, el punto de entrada falla en `AttributeError` —y `pip check` responde «No broken requirements found» con rc=0—. Un simple `pip install translate` del usuario habría bastado para romper la CLI sin un diagnóstico útil. Contraejemplo con el wheel real: `pip install translate` encima del paquete, `aipmt --help` rc=0 antes y después; ambas CLI coexisten.
    - **Nombre de distribución largo, comando corto.** `ai-powered-markdown-translator` hace que el paquete sea localizable mediante una búsqueda en PyPI; un acrónimo por sí solo sería imposible de encontrar para quien no conozca ya el proyecto, precisamente cuando la publicación busca ser descubierta. Se descartaron dos candidatos plausibles tras verificarlos: `ai-markdown-translator` está OCUPADO en npm desde 2024 por una herramienta con el mismo propósito, anterior a este repositorio en 17 meses; y `aimt` difiere en una letra de `aim` (v3.29.1), un paquete activo del MISMO ámbito —la peor configuración para una confusión duradera—. Trampa metodológica adicional: `pypi.org/project/<nom>/` devuelve 200 para cualquier nombre (página anti-bot); solo la API JSON es fiable.
    - **Layout `src/` en lugar de un paquete plano.** El paquete plano habría conservado los seis `sys.path.insert(..., "..")` de las pruebas, y ese es precisamente el defecto: hacen importar el árbol de código fuente en lugar del paquete, lo que ocultaría cualquier error de empaquetado. Coste real: una regla de sustitución adicional.

  - **Corrección: el `.env` del usuario se ignoraba una vez instalado el paquete.** `load_dotenv()` sin argumentos no asciende desde el directorio actual, sino desde el archivo LLAMADOR, es decir, desde `site-packages`. Medido con un punto de entrada de consola real ejecutado desde un proyecto con su propio `.env`: `find_dotenv()` devuelve `''` y la clave no se carga, mientras que `find_dotenv(usecwd=True)` sí la encuentra. El error no existía mientras la herramienta solo se ejecutaba desde el repositorio clonado; la publicación lo habría vuelto sistemático, con el único síntoma de una clave de API «faltante» en una configuración correcta.

  - **Tres gates habrían pasado a verde tras dejar de verificar nada.** Se endurecieron ANTES del desplazamiento, deliberadamente: una salvaguarda escrita después del cambio que debe detectar no demuestra nada. Cada una aparece en verde en el repositorio original y pasa a rojo en una copia migrada; se miden ambas direcciones.

    - **Lizard ignora una ruta ausente sin decir nada**: rc=0, «0 file analyzed». El gate de complejidad habría pasado de 158 funciones / 2247 nloc a 3 funciones / 34 nloc, con una salida de cero bytes. El alcance es ahora una matriz cuya existencia se verifica para cada entrada.
    - **`coverage run --source=` sobre un módulo ausente no falla**: advertencia solo en stderr, rc=0 tanto para unittest como para `coverage xml`, y el informe se publica igualmente —recortado de 1453 a 141 statements—. El proyecto habría parecido sano porque apenas se analizaba. Dos umbrales mínimos protegen el informe: el total y el archivo más grande medido.
    - **La sonda de actualidad de las traducciones es estructuralmente ciega a la forma de invocación**: se basa en los flags de argparse, precisamente aquello que un cambio de nombre de archivo no modifica. Reproducido: módulo desplazado, los 15 README siguen documentando un comando inexistente y el veredicto es «ninguna traducción obsoleta». Por tanto, una séptima sección verifica la FORMA y no las opciones, y el hook de Lizard se contrasta con el alcance real del script: su clave `files:` no hace fallar pre-commit cuando deja de coincidir, sino que hace que se OMITA.

  - **`requires-python = ">=3.10"` deja de ser una afirmación.** `sonar-project.properties` ya anunciaba 3.10-3.12 sin que nada lo hubiera ejecutado jamás; el entorno de desarrollo solo tenía 3.12, una contradicción interna que la publicación habría hecho pública. Ahora un workflow de pruebas ejecuta la suite en 3.10, 3.11 y 3.12, instalando el PAQUETE y, por tanto, sus límites públicos.

  - **Límites inferiores, ningún tope superior.** `requirements.txt` sigue siendo el lock probado, `[project.dependencies]` se convierte en el contrato público: publicar las versiones exactas del lock provocaría conflictos para cualquier usuario que tenga otros paquetes. Tampoco hay un tope `<N+1`: entraría en contradicción frontal con `check-deps-fresh.sh`, que hace fallar el gate de release ante cualquier retraso de versión mayor. El conjunto de límites inferiores resuelve el problema, y el contraejemplo `openai==1.0.0` termina en `ResolutionImpossible`, lo que demuestra que el control discrimina en lugar de aceptarlo todo. Además, una salvaguarda impide que la versión de `pyproject.toml` diverja de la del CHANGELOG: PyPI no permite reutilizar un número.

  - **Verificado de principio a fin en un venv nuevo**: wheel de 69 768 bytes que contiene únicamente `aipmt/*.py`, el dist-info y la licencia; `aipmt --help` rc=0 con 22 flags; `python -m aipmt` muestra «usage: aipmt» y no «usage: \_\_main\_\_.py»; instalación `pipx` funcional; y, sobre todo, **una traducción real de fr→en desde cualquier directorio del usuario**, con negrita, lista, código inline, enlace y URL preservados, y bloque de código sin traducir. Las 318 pruebas pasan con una lista de identificadores idéntica byte por byte antes y después de la migración: eso es lo que demuestra que ninguna prueba se neutralizó, no el «OK».

- **1.10.0** Proveedor `--use_codex` (cuota de suscripción de ChatGPT), actualización de los SDK y modelos, corrección de las citas de noticias en varios párrafos (2026-08-29):

  - **Revisión de seguridad: dos salvaguardas que la PR establecía sin mantenerlas en todas partes**:

    - **El preflight de Codex transmitía todo el `.env` al binario.** `_codex_preflight` llamaba a `subprocess.run` **sin `env=`**: el subproceso heredaba el `os.environ` completo y, por tanto, la totalidad del `.env` cargado por `load_dotenv`. Medido con un binario falso instrumentado: **siete secretos** llegaban al preflight —las claves de los seis proveedores más un `GITHUB_TOKEN`—, frente a **cero** en su homólogo `_grok_preflight`, que sí pasaba `env=_grok_env()`. La incoherencia era interna a la PR: `_strip_secret_env` existe precisamente para mantener este invariante, a unas pocas líneas de distancia. Se extrae y comparte un `_codex_env_base()` entre ambas rutas; medición tras la corrección: 0 secretos en ambos lados.
    - **La propiedad «`--deny` fail-closed» no cubría la forma utilizada.** El comentario justificaba todo el confinamiento de Grok por el hecho de que una regla con prefijo desconocido hace rechazar el inicio. Medido en `grok 1.0.13`, esta validación existe **solo para la forma entre paréntesis**: `--deny 'CeciNestPasUnOutil(*)'` rechaza el inicio («unknown tool prefix»), mientras que `--deny 'CeciNestPasUnOutil'` se acepta silenciosamente. Sin embargo, `GROK_DENY_RULES` solo empleaba nombres desnudos; un cambio de nombre de herramienta por parte de xAI habría eliminado la única capa de confinamiento medida sin ninguna señal, en un equipo donde el sandbox del sistema operativo ya no se aplica. Las ocho reglas con nombre pasan en `Prefix(*)`, cada una verificada como prefijo conocido de la CLI; el catch-all `*` conserva su forma literal, la única aceptada. Una prueba impide volver a la forma no validada.
    - **Verificado correctamente en los demás aspectos**: ninguna inyección de comandos (forma de lista en todas partes, nunca `shell=True`, contenido del documento mediante stdin o `--prompt-file`), ninguna deserialización insegura (`json.loads` únicamente, con comprobación de tipo), corrección de recorrido de rutas sin encontrar evasiones en siete cargas útiles, y `--deny '*'` aplicado efectivamente por la CLI (`DENY_ENFORCED` observado en una lectura fuera de workdir).
    - El control de actualidad añadido anteriormente también eludía su propio principio: un paquete cuya consulta a PyPI fallaba se omitía silenciosamente y el gate quedaba en verde. Ahora cuenta los paquetes realmente comparados y falla si la cobertura es incompleta.

  - **Dependencias actualizadas, y dos redes para impedir que el retraso se repita**:

    - **El retraso era real y duradero**: `openai` 2.54 → **3.6.0**, `anthropic` 0.125 → **1.2.0**, `certifi` 2024.8.30 → **2026.7.22**: dos años de retraso en el almacén de certificados raíz que valida TLS para todas las llamadas de los proveedores. Causa identificada: **no existía un `.github/dependabot.yml`**. Sin este archivo, GitHub solo activa las _security updates_, y Dependabot solo propone una PR para una dependencia afectada por una CVE, lo que explica que actualizara `urllib3` y `idna` mientras dejaba que dos SDK se desviaran una versión mayor.
    - **Las dos versiones mayores coexisten sin conflicto**, al contrario de lo que hacía temer un razonamiento anterior: `openai` 3.x y `anthropic` 1.x migran a **`httpx2`** mientras `mistralai` y `google-genai` permanecen en `httpx<1`, pero son dos distribuciones distintas. Verificado mediante una instalación real y después mediante **las 7 rutas de proveedor probadas de principio a fin** —OpenAI, Claude, Mistral, Gemini, Grok API, Codex CLI y Grok CLI—, con código inline y enlaces preservados en cada salida. «Evitar dos pilas HTTP» era una preferencia, no un bloqueo: la medición zanjó la cuestión.
    - **`requirements.txt` no describía el entorno real**: `google-auth`, `cryptography` y la pila `opentelemetry` estaban instalados en el venv de trabajo sin estar declarados; por tanto, una instalación limpia no reproducía lo que se probaba. En cambio, `tokenizers`, `huggingface-hub` y `PyYAML` figuraban allí sin ser importados ni requeridos por nada, residuos de `mistralai` 1.x. El archivo se regenera como el cierre completo de un venv construido a partir únicamente de las dependencias directas. `pip-audit` no informa de ninguna vulnerabilidad conocida en el nuevo conjunto.
    - **`.github/dependabot.yml`** (nuevo) activa actualizaciones semanales de versiones, pip y github-actions. Las actualizaciones menores y los parches se agrupan en una PR —un bump de parche por PR acaba siendo ignorado, y el ruido es enemigo de la actualización—; **las mayores se separan**, y cada una exige validación mediante una llamada real.
    - **`scripts/check-deps-fresh.sh`** (nuevo, conectado al gate) hace visible el retraso en el veredicto del proyecto: Dependabot propone, no garantiza, y sus PR pueden acumularse. Retraso de versión mayor → fallo; menor → advertencia, porque un gate rojo permanente acaba siendo ignorado; PyPI inaccesible → omisión explícita en local y **fail-closed en CI**, ya que un control no ejecutado no es un éxito. Verificado en ambas direcciones: detecta exactamente el estado anterior a la corrección (`openai 2.54.0→3.6.0`, `certifi 2024.8.30→2026.7.22`) y se limita a advertir sobre una versión menor.

  - **Correcciones derivadas de la revisión de esta PR**: cinco agentes de revisión examinaron el diff con lupa; todos los puntos siguientes fueron **reproducidos mediante mediciones** antes de corregirse, y dos de ellos eran regresiones introducidas anteriormente en esta misma versión.
- **Regresión corregida: `_NEWS_CITATION_REGEX` tenía backtracking exponencial.** El fix multipárrafo había introducido `(?:[ \t]*$|[ \t]+.*)` en la repetición: el reparto de los espacios entre `[ \t]+` y `.*` es ambiguo, y esa ambigüedad se multiplica de una iteración a otra. Medido con líneas `>   texte` —una indentación Markdown perfectamente legal— que no coinciden con el patrón: **2 589 ms para 14 líneas** frente a 0,04 ms después de la corrección, con un factor de ~9 por cada línea añadida. En modo `--news`, un blockquote largo y no conforme bastaba para bloquear la traducción hasta el timeout del job, sin una causa identificable. La repetición consume ahora la línea completa de una sola vez (`\n^>(?![ \t]*—).*`), lo que deja una sola forma de coincidir en cada iteración. Verificado en el corpus real de 231 artículos: **cero diferencias** de captura, las mismas 423 citas y los 14 cuerpos multipárrafo siguen ampliándose.
    - **Dos flags de provider simultáneos facturaban por uso, en silencio.** Se aceptaba `--use_codex --use_mistral`; `_select_provider_client` probaba Mistral primero y `_resolve_provider` daba prioridad a los booleanos explícitos: ambos convergían en Mistral. El usuario solicitaba su cuota de suscripción y obtenía facturación por uso, sin la menor advertencia: exactamente el modo de fallo que `--use_codex` existe para impedir. Los seis flags de provider pasan ahora por un `add_mutually_exclusive_group`. **Cambio de comportamiento**: una línea de comandos que combine dos providers, aceptada hasta ahora silenciosamente, falla ahora en `argument --use_mistral: not allowed with argument --use_codex`.
    - **El gate de fin de trabajo pasaba a verde cuando sus sondas fallaban.** Cuatro de las trece comprobaciones de `scripts/check-release-ready.sh` seguían el patrón «capturar stdout, concluir si está vacío» sin consultar nunca el código de retorno: una excepción (archivo renombrado, `FileNotFoundError`) escribía en stderr, dejaba stdout vacío y la comprobación concluía «nada que señalar». La trampa «un `exit 0` no demuestra nada» se reprodujo dentro del script escrito para impedirla. Un helper `probe()` exige ahora código de retorno nulo **y** sentinela de finalización, y las sondas se niegan a concluir a partir de un conjunto vacío de indicadores: una aserción sobre un conjunto vacío siempre es verdadera. Demostración: la adición del grupo exclusivo anterior hizo pasar los flags de provider por un objeto `*_group`, que la antigua regex `parser\.add_argument\(` ya no coincidía; **seis flags de veintiuno** quedaban fuera del alcance en silencio, con el gate en verde.
    - **El escaneo de secretos no detectaba cuatro de seis providers.** La clase `[A-Za-z0-9]` excluye el guion: `sk-proj-…` (formato actual de OpenAI) y `sk-ant-api03-…` fallaban con su segundo guion, y `AIza…` no estaba cubierto. Patrón ampliado, `.secrets.baseline` excluido del escaneo. Además, la protección `.env` consultaba `git diff --cached`, que solo ve el índice: un `.env` **ya commiteado** —el peor caso— nunca aparecía allí. Ahora consulta `git ls-files`.
    - **El «calentamiento del token» de Codex no lo era.** Medido: `codex login status` no toca `~/.codex/auth.json` (mtime y tamaño sin cambios); su ayuda dice «Show login status». Sin embargo, el comentario afirmaba que actualizaba el token «una vez, secuencialmente», neutralizando así el riesgo de refresh concurrentes sobre un token rotativo de un solo uso. La protección anunciada no existía; ahora el comentario describe lo que hace el código, y la verdadera solución sigue siendo `max_jobs=4`. Además, la comprobación respeta `CODEX_BIN`, que ignoraba: un equipo sin `codex` en el `PATH` fallaba con «no autenticado», un diagnóstico engañoso.
    - **`.env` se obtenía en un subshell.** `detect_provider` se llama mediante sustitución de comandos, por lo que sus exports no se propagaban: un `GROK_BIN`, `GROK_HOME` o `REGEN_MODEL` definido en `.env` permanecía invisible para las lecturas realizadas en `main()`, que concluía «binario Grok no encontrado» con una configuración correcta.
    - **La concurrencia superaba en un 50 % el límite anunciado.** La protección estaba situada después de iniciar el par README/CHANGELOG: pico medido de **3 para `max_jobs=2`**. En Grok, cuyo cupo semanal se comparte con Chat/Imagine/Voice y no se puede medir, el límite que se imponía el script no se respetaba. El recuento final, por su parte, se mostraba sin compararse nunca con 28: un archivo faltante pasaba inadvertido.
    - **Contrato de salida de Grok: la ausencia de un `stopReason` ahora es un fallo.** El código aplicaba «`end_turn` **o ausente**» donde el contrato anunciado exige `end_turn`. Un payload sin el campo —o cuyo campo fuera renombrado por una actualización del CLI— convertía la protección en un no-op silencioso. Además, `max_turn_requests` ya no se clasifica como rate limit (lo que se agota es el presupuesto de turnos: reintentar reproduce el resultado, a costa de esperar 90 s), y `quota` sale de los marcadores de rate limit, por la razón que el docstring de `_codex_is_rate_limited` ya explicaba sin que Grok la aplicara.

Una advertencia repetida cientos de veces deja de leerse; así es como se convierte en una máscara.

Medido: **otros siete secretos** entraban aun así en cada subproceso: las claves de Anthropic, Mistral, Google y Gemini, la del otro CLI y `OPENAI_BASE_URL`, que no es un secreto, pero redirige el tráfico. Ahora bien, ambos CLI son **agentes**, y el de Grok funciona sin sandbox del sistema operativo aplicable en muchos equipos Linux. El filtrado se realiza ahora **por patrón de nombre** (`API_KEY`, `_TOKEN`, `SECRET`, `PASSWORD`, `CREDENTIALS`) y no mediante una lista nominal, lo que también cubre las variables que un usuario añada en su `.env` sin que este código las conozca. Ninguna es necesaria para los CLI: la autenticación vive en `~/.codex` y `~/.grok`, nunca en el entorno; verificado mediante una **traducción real completada** con cada uno de los dos providers usando el entorno endurecido.

Esta última aserción es **genérica**: falla ante una clave que ninguna lista nombre, mientras que el test de expurgación existente era un espejo de su constante y no podía detectar nada salvo el fallo de su propio bucle. Suite completa: **311 tests**.

Solo fue necesaria una adaptación, que beneficia a todos: `finish_reason` ahora acepta `end_turn`, la forma que emite xAI allí donde OpenAI emite `stop`. Modelos: `grok-4.6` (calidad) y `grok-4.3` (económico). Cabe señalar que el modelo económico de Grok sigue siendo el más caro del repositorio: $1.25/$2.50 por millón frente a $0.15/$0.60 para `mistral-small-latest`; este provider se elige por la diversidad de modelos, no por el precio.

El lanzamiento de subprocesos se factoriza con Codex en `_codex_run_process`, sin tocar el resto del provider Codex ya probado.
    - **`exit 0` no demuestra nada, medido**: sin autenticación, el CLI escribe `{"type":"error","message":"Not signed in."}` en **stdout** con un código de retorno **0**. Un rechazo o un agotamiento de turnos se comportan igual. Por tanto, el contrato de salida exige simultáneamente cuatro condiciones: código de retorno 0, ausencia de payload de error, `stopReason == end_turn` y texto no vacío. El preflight sigue la misma lógica: `grok models` devuelve 0 incluso desconectado; solo la presencia de «not authenticated» en stdout permite concluir.
    - **Confinamiento: asimetría asumida y documentada.** Mientras Codex se ejecuta en `--sandbox read-only`, el sandbox de Grok resulta inaplicable en muchos equipos Linux recientes por dos causas del sistema independientes e imposibles de sortear sin `sudo`: AppArmor bloquea los user namespaces sin privilegios desde Ubuntu 24.04 (`bwrap: setting up uid map: Permission denied`, reproducido fuera de Grok), y la deny-list de sockets de runtime de contenedores falla cuando `/run/podman` está en `0700` (el resolver solo recupera `ErrorKind::NotFound`; EACCES se vuelve fatal). Trampa central: un perfil **integrado** que no puede aplicarse **se inicia sin confinamiento y en silencio**. Por ello, el script no solicita ningún perfil de forma predeterminada ni vuelve a un modo no confinado silenciosamente: advierte en stderr. La protección se basa en las reglas `--deny` del CLI, incluido el catch-all `*`, la única capa medida _fail-closed_ (una regla con un prefijo desconocido hace que se rechace el inicio). `GROK_TRANSLATE_SANDBOX=read-only` permite exigirlo; en ese caso, el inicio falla si la máquina no puede cumplirlo.

    - **Cuota**: el pool de Grok es semanal y **compartido con Chat, Imagine y Voice**, y ningún comando lo expone, a diferencia de Codex, cuyo `account/rateLimits/read` permite cuantificar el consumo. `regen_translations.sh` limita por tanto la concurrencia a 2 y advierte explícitamente.

- **1.9.2** Corrección de la extracción de la URL de atribución de noticias con paréntesis anidados o prefijo FR (2026-05-11):

En una atribución del tipo `(relayé par [@user sur X](https://x.com/.../123))` (paréntesis anidados: `(` envolventes + `]()` del enlace markdown), la captura se detenía en el primer `)` encontrado → cadena truncada y con el prefijo FR incluido: `relayé par [@user sur X](https://x.com/.../123` (sin el `)` final).
