- **1.16.0** Provider `--use_claude_code`: tłumaczenie w ramach limitu subskrypcji Claude Pro lub Max za pomocą oficjalnego CLI `claude -p` — brak płatnych ścieżek, a każde wywołanie to potwierdza (2026-09-26):

  - **Jedenasta ścieżka: subskrypcja Claude, bez rozliczania według zużycia.** `--use_claude_code` steruje oficjalnym plikiem binarnym Claude Code w trybie `-p`, na tej samej bazie co Codex, Grok CLI i Antigravity — czysta grupa procesów, bezpieczne zatrzymanie po upływie limitu czasu, Ctrl-C lub zamknięciu terminala. Nie należy mylić z `--use_claude`, czyli API firmy Anthropic rozliczanym według zużycia. aipmt nigdy nie odczytuje tokena.

  - **Brak płatnych ścieżek, weryfikowany na trzech poziomach.** Środowisko podprocesu stanowi listę dozwolonych: brak klucza API, tokena, dostawcy chmurowego czy jakiegokolwiek znacznika sesji Claude Code, z której aipmt zostałby uruchomiony — ta, która napisała ten provider, eksportowała ich piętnaście. Weryfikacja wstępna (preflight), bez wykonywania tury modelu, wymaga od `claude auth status` logowania subskrypcyjnego bez klucza Console, a od `/usage` frazy poświadczającej subskrypcję. Następnie każde wywołanie musi to poświadczyć w swoim zdarzeniu inicjalizacji — `apiKeySource: none`, prawidłowo odebrane wymuszone środowisko, model z żądanej rodziny, brak trybu szybkiego — oraz w zestawieniu limitów: płatne „extra usage” natychmiast zatrzymuje tłumaczenie.

  - **Limit jest współdzielony z sesjami Claude Code, a provider go oszczędza.** Każde wywołanie raportuje wykorzystanie okien 5-godzinnych i tygodniowych; powyżej 80% (`AIPMT_CLAUDE_MAX_UTILIZATION`) żaden kolejny segment nie jest uruchamiany. W dniu pisania limit tygodniowy konta autora wynosił już 98%.

  - **Nic z konfiguracji użytkownika nie przenika, nic z sesji nie pozostaje.** Bez narzędzi, w trybie bez personalizacji, zignorowane ustawienia użytkownika, odłączone serwery MCP i hooki, prywatny i jednorazowy katalog roboczy, brak zapisywanych transkrypcji. Zmierzone za pomocą wartości kontrolnych (canary): bez `CLAUDE_CODE_DISABLE_ATTACHMENTS` parametr `@chemin` dokumentu stawał się załącznikiem, a model zwracał wywołanie odczytu zamiast tłumaczenia; z nim nic nie przechodzi. Wartości kontrolne `AGENTS.md`, `CLAUDE.md` i hook niczego nie załadowały ani nie wykonały.

  - **Segment zaczynający się od `/` nie docierał do modelu.** W trybie `--disable-slash-commands` Claude Code sam odpowiada na to „… isn't available in this environment.” ze statusem `success`, bez żadnej tury. Znak nowej linii przed segmentem przesyła go do modelu; kontrakt wyjściowy i tak odrzuca odpowiedź zwróconą bez tury, w więcej niż jednej turze, obciętą lub pochodzącą z innego modelu niż zadeklarowany.

  - **Modele: aliasy, nigdy sztywny identyfikator.** Domyślnie `sonnet`, przy nakładzie pracy (effort) `low`, a także w trybie `--eco` — `--eco` nie zmienia więc niczego na tej ścieżce —, `opus` oraz `haiku` poprzez `--model`; `fable` i warianty `[1m]` są odrzucane, ponieważ w `-p` przełączają się na płatne kredyty bez pytania.

  - **Wady są mierzone, a nie zakładane.** Za pomocą samego `aipmt --use_claude_code`, cztery równoległe tłumaczenia na dwóch dokumentach pomiarowych z README — gęstym artykule przeglądowym w `--news` oraz tym README w wersji 1.14.0 — po czternaście języków każdy. `sonnet`, przy nakładzie pracy `low`, wykonuje 28 tłumaczeń, z czego 26 bez żadnych rozbieżności: jedno dodatkowe pogrubione słowo po chińsku w artykule, a po arabsku w README wiersz tabeli przyklejony do poprzedniego, co jest maskowane podczas renderowania. Nienaruszone linki wewnętrzne, angielskie cytaty skopiowane bez zmian, a w języku angielskim wiersze francuskiego tłumaczenia usunięte przez model, bez zmyślonych flag; mediana czasu na język wyniosła 6 min 49 s dla artykułu oraz 2 min 20 s dla README. `opus` tłumaczy README bez żadnych rozbieżności, o jedną czwartą szybciej, ale nie przetłumaczył żadnego artykułu: jego zabezpieczenia (guardrails) zatrzymały odpowiedź we wszystkich czternastu językach przy krótkiej notatce biologicznej. Z kolei `haiku` pisze wszystko — trzy nagłówki sekcji zmienione na poziom 1 w artykule, zduplikowane linki wewnętrzne w angielskim README —, ale dwukrotnie wolniej niż `sonnet`: rozumuje bez możliwości wyłączenia tego, co stanowi 61% jego tokenów wyjściowych, a jego niższa cena daje zaledwie 14% oszczędności w przeliczeniu na ekwiwalent API. Stąd wybór `sonnet` również w trybie `--eco`. Nakład pracy (effort) nie daje nic przy tłumaczeniu: we wstępnej partii — to README i ten CHANGELOG w języku angielskim, japońskim i hindi — `sonnet` nie wygenerował żadnych tokenów rozumowania, `opus` przy średnim nakładzie wygenerował 1% swoich tokenów wyjściowych, a średni nakład nie przyniósł żadnej przewagi nad niskim, ani pod względem struktury, ani czasu. Kampania `sonnet`, licząca 1,8 miliona znaków źródłowych, zużyła 9 punktów procentowych z 5-godzinnego okna i 2 z tygodniowego w ramach subskrypcji Max autora — i to z naddatkiem, ponieważ sesja sterująca pomiarami korzystała z tego samego limitu.

  - **Odmowa ze strony zabezpieczeń Anthropic jest wprost tak nazywana.** Opus 5.5 ma bardziej rygorystyczne zabezpieczenia niż Sonnet, a komunikat o błędzie Anthropic ostrzega, że czasami oznaczają one treści zbliżone do badań biologicznych. Wystarczyła krótka notatka przeglądowa o 279 cząsteczkach wygenerowanych dla miejsca wiązania. Claude Code przerywa wtedy odpowiedź, ponawia próbę jeden raz, po czym model zwraca „I can't continue this translation” ze statusem sukcesu, bez błędu, w dwóch turach: jedynie kontrakt pojedynczej tury zatrzymywał taką odpowiedź, nie podając jej przyczyny. Wysłana osobno, notatka zostaje odrzucona przez API w ramach kategorii „bio”. aipmt rozpoznaje teraz te oznaki, wskazuje zabezpieczenia oraz ich kategorię, nie ponawia próby — ten sam tekst wywołałby tę samą odmowę — i zaleca `--model sonnet`, który przetłumaczył notatkę na wszystkie czternaście języków.

  - **Tłumaczenia tego repozytorium mogą korzystać z tej ścieżki bez wyjątku.** `REGEN_PROVIDER=claude_code` to subskrypcja, a nie płatne API: działa bez `REGEN_ALLOW_PAID_API`, z czterema zadaniami — kampanie działały przy czterech jednoczesnych tłumaczeniach bez żadnego błędu przepustowości ani blokady połączenia —, po pojedynczym preflightcie, który nie zużywa limitu. Domyślnym wyborem pozostaje Codex z `gpt-5.6-sol`.

  - **Warunki korzystania określone bez ogródek.** Strona prawna Claude Code nie zabrania użytkownikowi łączenia się z niezmodyfikowanym plikiem binarnym przy użyciu własnej subskrypcji; zabrania jednak zewnętrznym deweloperom przesyłania żądań przy użyciu danych logowania Pro lub Max ich użytkowników, a Anthropic preferuje klucz API w przypadku narzędzi innych firm, w tym projektów open source, zastrzegając sobie prawo do rozliczania ich użycia z płatnych kredytów. Żaden zapis nie rozstrzyga jednoznacznie przypadku dystrybuowanego narzędzia, które uruchamia oficjalny plik binarny: użytkownik działa na własną odpowiedzialność w ramach swojego konta.

  - **Testy**: nowy plik `tests/test_claude_code_provider.py` (58 testów), 100% instrukcji i gałęzi modułu, bez uruchamiania prawdziwego `claude` — wyczyszczone środowisko, nieistniejący plik binarny, `PATH` bez `claude`, dublerzy (test doubles) zgłaszający błąd przy wywołaniu.

- **1.15.0** Provider `--use_antigravity`: tłumaczenie w ramach limitu subskrypcji Google AI Pro lub Ultra za pomocą oficjalnego CLI `agy`; a dla wszystkich providerów Ctrl-C nie porzuca już agenta w trakcie działania, pusty segment nie powoduje już awarii pliku, a projektowy `.env` nie decyduje już o uruchamianym pliku binarnym (2026-09-26):

  - **Dziesiąta ścieżka providera: subskrypcja Google, bez rozliczania według zużycia.** Każdy, kto opłaca Google AI Pro lub Ultra, może teraz rozliczać swoje tłumaczenia w ramach tego abonamentu zamiast płacić za tokeny w API Gemini. `agy`, oficjalne CLI narzędzia Antigravity, jest jedyną drogą do tego limitu: Gemini CLI od 18 czerwca 2026 roku nie obsługuje już kont Pro, Ultra ani bezpłatnych, a Antigravity SDK uwierzytelnia się wyłącznie za pomocą klucza API lub Google Cloud. `--use_antigravity` steruje nim w trybie headless, tak jak w przypadku Codexa i Grok CLI, na tej samej bazie — czysta grupa procesów, `SIGTERM`, a następnie `SIGKILL` po upływie limitu czasu, oczyszczone środowisko. Zweryfikowane kompleksowo na agy 1.2.11: przewodnik Markdown — front matter, pogrubienie, link w nawiasach, kod śródliniowy, blok kodu wcięty na liście, tabela, cytat — przetłumaczony na język angielski w 14 sekund wraz z preflightem, struktura identyczna ze źródłem, dodana nota tłumacza; następnie, po poprawkach z przeglądu, na niemiecki w 19 sekund, struktura identyczna, nic nie zostało zapisane w `~/.gemini`.

  - **Żadna płatna ścieżka nie pozostaje otwarta, a każde uruchomienie to weryfikuje.** agy obsługuje inne ścieżki niż subskrypcja — klucz API, projekt Google Cloud, bramę pośredniczącą, płatne kredyty AI — a kilka zmiennych środowiskowych przełącza go na nie bez wyświetlania jakichkolwiek komunikatów. Zmierzone: `AGY_GATEWAY_URL` wysyła dokument do zewnętrznej bramy, `AGY_ADC_AUTH` przełącza na rozliczany projekt Google Cloud, a `CLOUD_CODE_URL` przekierowuje uwierzytelniony punkt końcowy pod dowolny adres. Środowisko podprocesu stanowi zatem listę dozwolonych, a nie zablokowanych: `PATH`, język i strefa czasowa, terminal, tożsamość, proxy oraz certyfikaty maszyny i magistrala sesyjna — wszystko to, co według `env -i` jest niezbędne dla agy —, bez żadnego klucza. Lista zablokowanych oparta na rodzinach prefiksów (`AGY_`, `GOOGLE_`, `GEMINI_`, `CLOUD_CODE_`…), wypróbowana na początku, pomijała niektóre przypadki: przegląd ujawnił w ciągach znaków pliku binarnego nadpisania punktów końcowych, których nie obejmował żaden prefiks: `AICODE_ENDPOINT_URL`, `UNLEASH_URL`, `GCE_METADATA_HOST`. Dwa ustawienia wymykają się środowisku i można je odczytać tylko przez `agy -p /config`: płatne kredyty AI, które przejmują działanie po wyczerpaniu limitu, oraz połączenie przez projekt Google Cloud. Preflight, który nie zużywa limitu — zużycie równe zero, potwierdzone pomiarem — odmawia tłumaczenia, jeśli którekolwiek z nich jest aktywne lub jeśli skonfigurowano klucz API, a brak któregokolwiek z tych trzech ustawień w `/config` oznacza odmowę: nowa wersja agy, która zmieniłaby ich nazwę, nie może pozwolić na zaliczenie kontroli, która niczego nie sprawdziła. Wreszcie dziennik każdego wywołania musi poświadczać uwierzytelnienie subskrypcyjne (`authMethod=consumer`), a jakakolwiek inna metoda uwierzytelnienia, która się w nim pojawi — w jednej z dwóch pisowni stosowanych przez plik binarny — powoduje odrzucenie odpowiedzi: to samo wywołanie jest wiążące, a nie przygotowana konfiguracja.

  - **Agent tłumaczący nie ma żadnych narzędzi, a jego załadowanie jest weryfikowane przy każdym wywołaniu.** Każde wywołanie zapisuje w jednorazowym katalogu agenta w formacie agentów projektowych agy: `tools: []`, `excludeDefaultComponents: true`, `inheritCustomizations: false`. Około 800 tokenów wejściowych zamiast 12 400 w przypadku domyślnego agenta, a trzecie ustawienie nie jest zbędne: samo `excludeDefaultComponents` pozwalało hookowi przestrzeni roboczej na wykonywanie poleceń i wstrzykiwanie tekstu. Prawdziwa pułapka tkwi gdzie indziej: nieodnaleziony agent nie powoduje błędu agy. Kod wyjścia 0, status `SUCCESS`, i odpowiada agent programistyczny z 57 aktywnymi narzędziami — na „Le chat dort.” odpowiedział „Ciii, nie budźmy go! 🐱💤 Co mogę dziś dla Ciebie zrobić?”. Nic na stdout ani stderr: informuje o tym wyłącznie dziennik wywołania. Odpowiedź jest więc odrzucana, jeśli dziennik zgłasza takie wycofanie (fallback), a także jeśli nie zawiera pozytywnego znacznika załadowania agenta — zmiana formatu dziennika powoduje odrzucenie tłumaczenia zamiast cichego usunięcia zabezpieczenia. Każdy znacznik musi zajmować całą linię dziennika w zmierzonym formacie — poziom ważności, data, godzina, wątek, plik i linia: plik binarny zawiera również wiersz kopiujący wiadomość użytkownika do dziennika — czego nigdy nie zaobserwowano przy domyślnym poziomie logowania w 78 rzeczywistych dziennikach —, a dokument cytujący te wiadomości nie może spełniać warunku zabezpieczenia zamiast agy.

  - **Ustawienia i historia agy użytkownika pozostają nienaruszone.** Każde wywołanie działa z prywatnymi katalogami HOME, tymczasowym i roboczym, usuwanymi po zakończeniu. agy i tak uwierzytelnia się za pośrednictwem systemowego pęku kluczy, którego aipmt nigdy nie odczytuje. Nic nie jest dziedziczone: ani uprawnienia użytkownika — które pozwalały domyślnemu agentowi uruchamiać `ls` i `git` bez pytania —, ani jego globalne reguły, wtyczki, serwery MCP, hooki i umiejętności (skills). Nic też nie trafia do jego historii, w której każde wywołanie pozostawiało konwersację o rozmiarze około 200 KB wraz z przetłumaczonym tekstem: seria prób pozostawiła tam około 95 konwersacji i wyparła 17 wpisów z pamięci podręcznej ograniczonej do 100. Sprawdzone: żaden plik nie został zapisany w `~/.gemini/antigravity-cli`.

  - **Odmowa domyślna tam, gdzie izolacja nie zadziała.** W systemie Linux bez magistrali sesyjnej D-Bus — sesja SSH, kontener, serwer — agy przechowuje swój token w pliku w `~/.gemini` zamiast w pęku kluczy, jak podano w jego własnym changelogu (1.1.3), a izolacja każdego wywołania ukrywa ten plik. Odmowa następuje teraz przed jakimkolwiek uruchomieniem, z podaniem rzeczywistej przyczyny, zamiast minutowego oczekiwania na kod logowania, po którym następowała bezużyteczna sugestia ponownego połączenia. W systemie Windows agy odczytuje `USERPROFILE`, `APPDATA` i `TEMP`, a nie `HOME` ani `TMPDIR` — według dokumentacji języka Go i ciągów znaków w pliku binarnym — nic nie odizolowałoby tam wywołania od ustawień ani historii użytkownika, dlatego `--use_antigravity` jest tam odrzucany, dopóki nie zostanie to zmierzone. macOS działa, choć nie został zmierzony; zabezpieczenie rozliczeniowe, które odczytuje rzeczywistą konfigurację, zachowuje tam swoją skuteczność.

  - **`exit 0` niczego nie dowodzi, czwarte CLI.** Odpowiedź jest akceptowana tylko przy zerowym kodzie powrotu, obiekcie JSON o statusie `SUCCESS`, zgodnym dzienniku, braku odrzuconych akcji, poleceń czy błędów w JSON, braku ostrzeżeń o obcięciu na stderr oraz niepustym tekście. `--print-timeout` nie jest nigdy używane: po jego upływie agy zwraca częściowe wyjście w `SUCCESS` z kodem 0; limit czasu jest zewnętrzny i zabija grupę procesów. Segment zaczynający się od `/commande`, `!commande` lub `@fichier` jest tłumaczony, nigdy wykonywany ani rozwiązywany — bez `--disable-slash-commands` polecenie „/help” wykonywało się zamiast tłumaczenia. Pusty segment nie trafia już do agy, ponieważ potok zwraca go bez zmian (patrz niżej), i w ostateczności pozostaje odrzucany przed wywołaniem: przy pustym wejściu agy otwiera swój interfejs interaktywny z kodem 0. Ponowienie próby opiera się na polu `retryable` wiersza `AGY_ERROR`, który agy wypisuje na stderr od wersji 1.2.6: narzędzie samo ponawia już błędy przejściowe — 502, 503, 504, limit na minutę — i to ono wie, czy pozostały błąd nadal ma taki charakter. W przypadku braku tego pola nie następuje ponowienie, gdy komunikat mówi o wyczerpaniu zasobów — w Google `RESOURCE_EXHAUSTED` ma ten sam kod 429 co limit na minutę, ale wyczerpane 5-godzinne okno nie odnawia się w 90 sekund —, w przeciwnym razie tylko przy ograniczeniu przepustowości (rate limiting). Odpowiedź zachowuje zakończenie linii segmentu: agy zawsze kończy swoją odpowiedź znakiem nowej linii, co na łączeniu dzieliło na dwoje akapit rozcięty w środku zdania. Rozłączona sesja generuje komunikat informujący o konieczności uruchomienia `agy` w celu ponownego połączenia. `AGY_CLI_DISABLE_AUTO_UPDATE=true` zapobiega ostatecznie temu, by nowy HOME uruchamiał przy każdym wywołaniu moduł sprawdzania aktualizacji we własnej sesji poza zasięgiem limitu czasu — sama wartość `1` nie przynosi żadnego efektu.

  - **Modele: nakład myślenia jest częścią nazwy.** Identyfikatory odpowiadają tym z `agy models` — `gemini-3.8-flash-medium`, `gemini-3.7-flash-low`, `gemini-3.1-pro-high`, `claude-sonnet-4-6`… Sama nazwa bazowa, którą agy by odrzucił, jest odrzucana przed wywołaniem, wraz z istniejącymi sufiksami: `-medium` lub `-low` dla Flasha, `-high` lub `-low` dla Pro. Domyślnie `gemini-3.8-flash-medium`, a w `--eco` `gemini-3.7-flash-low`, ustalone na podstawie kampanii opisanych poniżej. `--reasoning_effort` nie ma wpływu i o tym informuje. Claude i GPT-OSS korzystają z odrębnego i znacznie mniejszego limitu — około 1% 5-godzinnego okna na zmierzone wywołanie, w porównaniu z 0,05% w przypadku Flasha — o czym przypomina ostrzeżenie. Pozostały limit można odczytać bezpłatnie za pomocą `agy -p /usage`. Odrzucane w CI, podobnie jak Codex i Grok CLI: logowanie znajduje się w osobistym pęku kluczy, a komunikat proponuje `--use_gemini` z kluczem Google.

  - **Dwie kampanie 26 września: wartości domyślne są mierzone, a nie zakładane.** Za pomocą samego `aipmt --use_antigravity`, cztery tłumaczenia równolegle, każde porównane ze swoim źródłem przez `scripts/compare_structure.py`, limit odczytany przez `agy -p /usage` przed i po. Rano, na rewizji tego README opublikowanej wraz z 1.14.0 oraz na gęstym artykule przeglądowym pomiarów z README, w `--news`, `gemini-3.7-flash-medium` pisze czternaście języków obu dokumentów: artykuł bez żadnych rozbieżności, mediana 3 min 14 s na język, a README z dokładnością do jednego pogrubionego słowa w języku koreańskim w 1 min 22 s. Po południu, na prośbę autora, Gemini 3.8 Flash kontra 3.7 na tej samej partii, tym README i tym CHANGELOGU w wersji 1.15.0: przy średnim nakładzie pracy ta sama struktura dla obu; 3.8 myśli tyle samo co 3.7 — 63% tokenów wyjściowych w porównaniu z 60%, odczytanych z JSON-a agy — i kosztuje o jedną siódmą limitu więcej, przy czasie dłuższym o jedną czwartą. Następnie powtórzona poranna kampania w `gemini-3.8-flash-medium`: czternaście języków na czternaście bez rozbieżności w artykule, mediana 3 min 59 s, podobnie jak w README, 1 min 43 s; linki wewnętrzne nienaruszone we wszystkich czternastu plikach README, podczas gdy 3.7 psuł je w języku włoskim; a w języku angielskim linie francuskiego tłumaczenia usunięte przez model, bez zmyślonych flag, angielskie cytaty nienaruszone. Stąd wartości domyślne: `gemini-3.8-flash-medium` oraz `gemini-3.7-flash-low` w `--eco`. - **1.13.0** Provider `--use_openrouter`: płatny router do ~430 modeli, w tym otwartych modeli chińskich (2026-09-05):

  - **Dziewiąta ścieżka providera, dostarczona wraz z ósmą.** Wersja 1.12.0 nie została opublikowana na PyPI: oba routery, OpenCode i OpenRouter, wychodzą razem. [OpenRouter](https://openrouter.ai) daje dostęp za pomocą jednego klucza do modeli, których żaden inny provider tutaj nie udostępnia — Kimi, Qwen, DeepSeek, Z.ai — w ramach pojedynczego kredytu rozliczanego według zużycia. Ponieważ punkt końcowy jest kompatybilny z OpenAI, klient jest taki sam jak dla xAI; **wszystko, co wyróżnia tego providera, sprowadza się do preflightu**, a każda z jego reguł wynika z pomiarów na API.

  - **Ten sam model jest serwowany przez dziesiątki dostawców hostingu o różnych limitach, a routing jest na to ślepy.** Zmierzone: 33 dostawców dla `z-ai/glm-5.2`, 23 dla `z-ai/glm-5.3-flash` — w tym jeden z limitem do **2 048 tokenów wyjściowych**. Jedno długie tłumaczenie na 23 trafiało więc ucięte, losowo, bez najmniejszego sygnału. Preflight odczytuje `/api/v1/models/{modèle}/endpoints`, odrzuca dostawców z limitem poniżej 8 000 tokenów wyjściowych, tych ze statusem obniżonym oraz tych, którzy nie deklarują żadnego limitu, po czym przypina pozostałych. `provider.only` **bez** `allow_fallbacks: false` to tylko preferencja: router wraca do odrzuconego dostawcy i przypięcie traci jakąkolwiek wartość. Jeśli żaden dostawca nie spełnia limitu, polecenie się zatrzymuje: tłumaczenie mimo to oznaczałoby zaakceptowanie cichego ucięcia, któremu ten preflight ma zapobiegać.

  - **Rozumowanie jest fakturowane według stawki wyjściowej i domyślnie aktywne w wielu modelach.** To samo zapytanie do `z-ai/glm-5.2`, odpowiedź „OK”: **107 tokenów dopełnienia przy domyślnych ustawieniach modelu, 2 z wyłączonym rozumowaniem**. W przypadku tłumaczenia, któremu rozumowanie nic nie daje, oznacza to współczynnik 18 na każdym segmencie każdego pliku. Jest ono zatem domyślnie wyłączone. **288 modeli na 431**, które je wymuszają (`reasoning.mandatory`), zwraca `400 « Reasoning is mandatory for this endpoint and cannot be disabled »`: dla nich preflight odczytuje akceptowane poziomy wysiłku i żąda najniższego (następny punkt) — wysiłek przydziela **procent `max_tokens`**, który rozumowanie zużywa w pierwszej kolejności, przez co losowo wybrana wartość przesuwa ryzyko pustej strony, zamiast je zmniejszać.

  - **Model, który narzuca rozumowanie, otrzymuje najniższy poziom wysiłku, jaki akceptuje, i to pomiary o tym przesądziły.** Pierwszym wyborem było niewysyłanie niczego, aby nie zgadywać za model. Przetestowany na `z-ai/glm-5.3-flash`, którego domyślną wartością katalogową jest `max`, wybór ten generował wyjście **obcięte przy 32 768 tokenach** przed końcem tłumaczenia — dwa języki na czternaście zostały utracone. Zwiększenie puli nic by nie zmieniło: poziom wysiłku przydziela mu pewien procent, więc rozumowanie rośnie wraz z nim. Provider odczytuje więc `supported_efforts` podczas preflightu i żąda najniższego, powracając do „niczego”, gdy katalog nie deklaruje żadnego użytecznego. Kontrpróba na problematycznym języku: kończył się niepowodzeniem z powodu wyczerpanego budżetu, obecnie przechodzi w 9 minut ze strukturą identyczną ze źródłem.

  - **Awaria nadrzędnego hosta nosi teraz swoją nazwę.** Router normalizuje ten przypadek do `finish_reason=error` z zerowym `native_finish_reason` — zmierzone dwukrotnie, na dwóch językach, przy dokładnie 750 sekundach. Ogólny komunikat odsyłał do szukania błędu w dokumencie lub w podziale na segmenty; teraz informuje, że awaria leży po stronie dostawcy i że ponowna próba często wystarcza.

  - **`finish_reason=length` z pustym wyjściem nie jest obcięciem.** To budżet zużyty przez rozumowanie przed pierwszym użytecznym znakiem — zmierzono 15 850 tokenów rozumowania na 148 użytecznych. Oba przypadki wymagają przeciwstawnych działań: zmniejszenie rozmiaru segmentów w pierwszym nic nie daje. Komunikat wyraźnie je rozróżnia. Dwa inne zabezpieczenia wynikają z pomiarów: router odpowiada **200 z treścią zawierającą wyłącznie błąd**, gdy nadrzędny host zawiedzie (`choices[0]` zgłaszał nieprzejrzysty `TypeError`, który ukrywał komunikat), a okno kontekstu jest odczytywane z katalogu i zapisywane w `MODEL_TOKEN_LIMITS` — `DEFAULT_TOKEN_LIMIT` jest fałszywe dla 44 modeli z katalogu, w tym dwóch z limitem do 4095 tokenów.

  - **Bezpieczeństwo: projektowy `.env` nie może już przekierowywać wywołań API.** `find_dotenv(usecwd=True)` szuka pliku począwszy od bieżącego katalogu i jego katalogów nadrzędnych: niezaufane drzewo katalogów — świeżo sklonowane repozytorium — mogło umieścić tam `OPENROUTER_BASE_URL`, `XAI_BASE_URL` lub `OPENAI_BASE_URL` (tę ostatnią odczytywaną bezpośrednio przez SDK) bez znajomości jakiegokolwiek klucza, a prawdziwy klucz, pochodzący ze środowiska lub konfiguracji użytkownika, trafiał następnie do nagłówka autoryzacji serwera zewnętrznego. Filtr opiera się na WZORCU, a nie na liście: sprawdzając zainstalowane pakiety SDK, odczytywanych jest dwanaście zmiennych routingu, w tym sześć przez samego klienta Anthropic — ręcznie spisane wyliczenie pominęłoby połowę z nich. Z warstwy projektu odrzucana jest zatem każda zmienna kończąca się na `_BASE_URL`, `_API_BASE` lub `_ENDPOINT`, proxy oraz magazyny certyfikatów (wskazanie kontrolowanego urzędu certyfikacji sprawia, że serwer przechwytujący staje się nie do odróżnienia od prawdziwego), jak również `XDG_CONFIG_HOME` i `APPDATA`: ich ustawienie pozwalało decydować, który plik stanowi warstwę użytkownika, a tym samym obchodzić filtr okrężną drogą. Zmienne te są akceptowane wyłącznie z dwóch warstw kontrolowanych przez użytkownika: wyeksportowanego środowiska oraz `~/.config/aipmt/.env`. Warstwa projektu jest ponadto odczytywana BEZ interpolacji: `load_dotenv` domyślnie rozwija `${VAR}`, a niezaufany `.env` zawierający `NOM_ANODIN=${OPENAI_API_KEY}` kopiował prawdziwy klucz pod nazwą, której filtrowanie podprocesów według wzorca nie rozpoznaje — trafiał on wówczas do środowiska `codex exec`, wbrew deklarowanemu niezmiennikowi. Odrzucenie wyświetla wreszcie tylko nazwę zmiennej: adres URL w postaci `https://${CLE}@hôte/` powodował wyciek interpolowanego klucza do logów, nawet gdy był odrzucany. Odrzucenie jest wypisywane na stderr wraz z instrukcją postępowania — firmowy przekaźnik deklaruje się w konfiguracji użytkownika.
  - **Fix: pula wyjściowa OpenRouter jest obliczana dla każdego wywołania.** `context_length` obejmuje wejście ORAZ uzupełnienie, a stała rezerwa skalibrowana pod tekst łaciński niczego nie ogranicza: według pomiarów tokenizatorem `o200k_base` 16 000 znaków to 3200 tokenów po francusku, ale 12 300 po japońsku i 17 500 w przypadku emoji. Budżet wynika zatem z tekstu rzeczywiście wysłanego, powiększonego o liczbę bajtów UTF-8: w przypadku każdego tokenizatora łączącego bajty — bajtowe BPE, SentencePiece z powrotem do bajtów, czyli rodzin stosowanych w katalogu — jeden token jest warty co najmniej jeden bajt, i jest to jedyne dostępne oszacowanie górne, gdy OpenRouter kieruje zapytania do dziesiątek nieznanych tokenizatorów. Żaden średni współczynnik nie był odpowiedni — ideogram z płaszczyzny dodatkowej schodzi do 1,33 bajta na token, a znak łączący do 1,00 — a wejście wraz z wyjściem mieszczą się teraz w oknie z założenia konstrukcyjnego. Segment zbyt gęsty dla wybranego modelu jest odrzucany przed wywołaniem, a nie po naliczeniu opłat.

- **1.9.2** Poprawka wyodrębniania adresu URL atrybucji newsów z zagnieżdżonymi nawiasami lub francuskim prefiksem (2026-05-11):

  - **Naprawiony błąd**: wyodrębnianie adresów URL atrybucji w `_protect_news_quotes` używało wyrażenia regularnego `re.search(r"\((.+?)\)", attribution)` (leniwe przechwytywanie w nawiasach). Przy atrybucji typu `(relayé par [@user sur X](https://x.com/.../123))` (nawiasy zagnieżdżone: obejmujący `(` + `]()` linku markdown) przechwytywanie zatrzymywało się na pierwszym napotkanym `)` → ucięty ciąg znaków + zawierający francuski prefiks: `relayé par [@user sur X](https://x.com/.../123` (bez końcowego `)`). Konsekwencja: `_validate_news_post` szukał tego ciągu w przetłumaczonym wyniku i systematycznie kończył się niepowodzeniem (z dwóch powodów: ucięty `)` + „relayé par” przetłumaczone na `relayed by`/`weitergeleitet von`/...). Pełna kaskada low → medium → high → gpt-5.5 nie mogła przejść pomyślnie.
  - **Poprawka**: wyrażenie regularne zmienia się na `re.search(r"\]\(([^)]+)\)", attribution)` — celuje bezpośrednio w `](url)` linku markdown, przechwytuje **wyłącznie czysty URL** (bez francuskiego prefiksu ani obcinania), niezmiennik zachowywany przez placeholdery `#URL{N}#` podczas tłumaczenia. Odporne na oba problematyczne wzorce:
    - `(relayé par [@account sur X](url))` — nawiasy zagnieżdżone
    - `via [@source](url)` lub `selon [@author](url)` — francuski prefiks bez nawiasów obejmujących
  - **Testy**: 2 nowe w `test_silent_failure.py` w klasie `TestNewsCitationExtraction`:
    - `test_extract_attribution_url_with_nested_parens` (dokładny odtworzony przypadek błędu Genspark CEO E2B)
    - `test_extract_attribution_url_with_french_prefix` (wariant z `via`)

- **1.9** Poprawka cichych błędów (silent-failure) + kompletny zestaw narzędzi jakościowych + wielopozycyjna notatka o tłumaczeniu (2026-05-07):
  - **Wielopozycyjna notatka o tłumaczeniu + format znacznika „embed card”**:
    - Nowe opcje CLI (addytywne, domyślne bez zmian → **non-breaking**):
      - `--note_position {top,bottom,both}` (domyślnie: `bottom`): umieszcza notatkę na górze, na dole lub w obu miejscach przetłumaczonego pliku.
      - `--note_format {legacy,marker}` (domyślnie: `legacy`):
        - `legacy` ściśle odtwarza zachowanie z wersji v1.8 (pogrubiony akapit `**…**`) **byte-for-byte**.
        - `marker` emituje niewidoczną definicję referencji linku Markdown (`[ai-translation-note-<placement>]: <> "v=1 source=… target=… model=… date=…"`), po której następuje **3-akapitowy cytat blokowy (blockquote)** o strukturze dostosowanej do renderowania w stylu karty repozytorium GitHub („GitHub repo embed card”): tytuł projektu w kodzie inline (`**\`ai-powered-markdown-translator\`\*\*`), opis przetłumaczony przez LLM oraz link CTA (`[Voir le projet sur GitHub ↗](URL)`) z widoczną strzałką. Możliwość wykorzystania podczas budowania przez wtyczkę remark (por. blog jls42.org → wtyczka `remark-translation-banner`).
    - **Niezmienniki nigdy niewysyłane do LLM**: tytuł repozytorium i adres URL GitHub są składane po stronie Pythona po przetłumaczeniu zdania opisowego. LLM nigdy nie widzi sluga `ai-powered-markdown-translator` ani `https://github.com/jls42/...`, co gwarantuje, że żaden renderer/wielkość liter/schemat nie zostanie zmodyfikowany.
    - **Wstawianie uwzględniające frontmatter (frontmatter-aware)**: w trybie `top` lub `both` notatka jest wstawiana **po zamykającym bloku `---`** frontmattera YAML (bezpieczeństwo Astro Content Collections / gray-matter). Funkcja pomocnicza `_split_frontmatter` wykrywa `---\n…\n---\n` na początku pliku i zachowuje jego integralność; **zgłasza `RuntimeError`** w przypadku otwartego frontmattera bez zamykającego znacznika (plik trafia do `failed_files` zamiast zostać zapisanym z błędnie umieszczoną notatką).
    - **Sanityzator modelu oparty na białej liście**: `_sanitize_model` zastępuje każdy znak spoza `[A-Za-z0-9._:/-]` znakiem `_`, z wartością zapasową (fallback) `unknown`, jeśli ciąg jest pusty. Dostosowuje do walidatora po stronie wtyczki remark Astro i neutralizuje znaki, które mogłyby uszkodzić format znacznika (spacja, cudzysłów, nawias, przecinek itp.).
    - **Refaktoryzacja wewnętrzna**: `_append_translation_note` (1 monolityczna funkcja) → 7 czystych funkcji pomocniczych (`_translation_note_invariants`, `_build_translation_note_phrase`, `_assemble_translation_note_paragraphs`, `_build_translation_note_source`, `_sanitize_model`, `_quote_lines`, `_split_frontmatter`, `_build_translation_note_block`, `_compose_with_notes`). Rozdzielenie buildera i composera (builder zwraca czysty blok bez separatora, composer nakłada `\n\n` w zależności od pozycji); produkcja i funkcja pomocnicza źródła współdzielą ten sam 3-akapitowy asembler.
    - **`_quote_lines` zachowujący puste linie**: poprzedza każdą linię prefiksem `> `, przekształcając puste linie w sam znak `>`. Pozwala to parserowi mdast widzieć 3 odrębne akapity w cytacie blokowym (tytuł / opis / link) zamiast jednego akapitu ze znakami nowej linii (line-breaks).
    - **Adaptacyjny `_build_translation_note_block`**: w zależności od liczby akapitów zachowanych przez LLM (3 = pełny format karty, 2 = zdanie + link, 1 = fallback). 1-akapitowy fallback **nie otacza już w `**...**`**, gdy wykryty zostanie link Markdown `](` (niestabilne renderowanie `<strong>` wokół linku).
    - **Kompatybilność wsteczna**: `getattr(args, "note_position", "bottom")` i `getattr(args, "note_format", "legacy")` po stronie `_compose_with_notes` — obiekty Namespace bez tych atrybutów (istniejące testy, zewnętrzne wywołania programistyczne) nadal działają bez modyfikacji.
